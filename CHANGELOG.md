Format follows [Keep a Changelog](https://keepachangelog.com/). Versioning follows [Semantic Versioning](https://semver.org/).

## [0.6.0] - 2026-07-29

Every tool apexe served over MCP was uncallable, and most of the ones that could
be called were spelled wrong on the command line. Both are fixed here, along with
the input validation that made the two most-used wrapped tools unable to do any
real work.

A second round of verification against real binaries over `apexe serve
--transport stdio` found seven more defects, fixed here as well: every tool with
subcommands ran the wrong command, 44% of them never reached a client at all,
and the ones that did described a different command's options. Those fixes are
verified by *executing* the wrapped binary rather than by asserting on the
rendered string — three of them rendered perfectly and failed only when run.

### Fixed

- **BREAKING: the MCP tool name is the `module_id` again, so advertised tools can actually be called.** apcore-mcp lists `display.mcp.alias` as the tool name but routes an incoming `tools/call` by treating the received name *as* a `module_id` and looking it up in the registry — there is no alias-to-id reverse map anywhere on that path. apcore-toolkit's `sanitize_mcp_alias` rewrites `.` to `_`, so a dotted `module_id` — the apcore convention, and what apexe emits — guaranteed `alias != module_id` and **every tool apexe exposed failed with `[ModuleNotFound]`**, including every button in the Explorer UI. The alias is now stripped before registration, so the name in `tools/list` is the name `tools/call` accepts: `cli.curl`, not `curl`. A2A was never affected — it keeps the id and the display name in separate fields (`skill.id` / `skill.name`) — and `mcp.description` / `mcp.guidance` still apply, since only the *name* is load-bearing for routing. The upstream defect remains; this works around it without touching the `module_id` that ACL rules, `--prefix` filtering, audit records and A2A skill ids are all anchored to.
- **BREAKING: flags are spelled the way the tool actually accepts them.** The renderer prefixed every input key with `--`, which is wrong for most of what a scan finds. **452 of the 1006 flags across the 42 built-in overlays (44.9%) are short-only** and need one dash: `ls -l` was emitted as `ls --l`, which BSD `ls` rejects outright, so **45 of `cli.ls`'s 47 properties were unusable**. `find`'s `-daystart` and `-regextype` are multi-character yet single-dash, which no "one character means one dash" heuristic recovers. And `_` → `-` is lossy, so a long flag containing an underscore could never round-trip. The scanner now records the literal token it saw as `x-apexe-flag` on the schema property and the renderer reproduces it, rather than trying to invert a lossy mapping.
- **BREAKING: a long option carries its value with `=`.** It was emitted as two argv entries, which silently breaks every option whose value is *optional*: `ls --classify never` lists a file named `never` and exits 2, while `--classify=never` works. GNU spells `--classify`, `--color`, `--hyperlink`, `--backup`, `--preserve`, `--reflink` and `--context` that way, and the schema records no marker distinguishing an optional value from a required one — so `=`, which options with a required value also accept, is the only form that is always right. Short options are the opposite case and still pass the value separately, since `-I=PATTERN` would pass a value beginning with `=`.
- **BREAKING: positional arguments are passed bare, in their declared order.** All 42 built-in overlays declare `positional_args`, and every one of them was emitted as `--name value`: `ls /tmp` went out as `ls --file /tmp`. Order was lost too — nothing recorded it, so `cp source target` depended on the order the caller happened to write the JSON keys in, and `cp` inverts its meaning if the two are swapped. Operands now carry `x-apexe-positional` with their index, are emitted after all flags, and are sorted by that index. `curl` masked this in every demo: it accepts `--url` as an equivalent long option, so the one positional anybody exercised happened to work by coincidence.
- **A positional no longer silently discards a same-named flag's description.** Building the schema inserted operands last and unconditionally, so `curl`'s `<url>` operand overwrote the `--url` property and took its documentation with it. The description is now inherited when the operand has none — the common case, since usage lines carry no prose — and a name that is both required as a flag and as an operand no longer appears twice in `required`.
- **Shell metacharacters are no longer rejected in parameter values.** The 15-character blacklist was carried over from the v0.1 prototype and guarded a threat that does not exist on this execution path: arguments reach the child through `Command::args()`, which passes argv straight to `execve`, and no shell is spawned anywhere (the single `zsh` invocation in `scanner::completion` runs a hardcoded constant with no interpolation). `;`, `|`, `&`, `$`, backtick and quotes are ordinary bytes in argv — they cannot start a command, open a pipe or expand a variable. Rejecting them bought nothing and **made `curl` unable to send a JSON body (`{"a":1}`) or a form (`a=1&b=2`), and `jq` unable to receive any filter containing `|`, `(`, `)` or `$`** — that is, unable to do the only thing `jq` does. `\0`, `\n` and `\r` are still rejected: the first is refused by `Command` anyway, and the latter two corrupt the audit log's line framing.
- **Option-injection is now blocked, which the old blacklist did not do.** `-` was not in that 15-character set, so a value of `--output=/etc/passwd` or `-K /etc/shadow` passed validation and was handed to the wrapped tool's own parser, which cannot distinguish it from an option the caller was never granted. Values that begin with `-` are now rejected. This matters more after the change above, because an operand reaches argv bare with no flag token in front of it. A JSON *number* is exempt, so a legitimate negative number still works; the same thing typed as a string is not, because the caller asked for text.
- **Values from binding files keep the strict character set.** `json_flag` and `command_parts` are build-time scan artifacts, not runtime data, so nothing legitimate puts a shell metacharacter in them and the conservative check stays useful there as a tamper signal. Applying one rule to both classes was the original mistake: it imposed a build-time constraint on caller-supplied data.
- **GNU-style operands are extracted at all.** The usage-line parser only understood the BSD spelling, where the ellipsis goes inside the brackets (`ls ... [file ...]`). GNU puts it outside and writes required operands bare and in caps, and **all 20 GNU tools checked spell them that way**: `ls [OPTION]... [FILE]...`, `cp [OPTION]... [-T] SOURCE DEST`, `mkdir [OPTION]... DIRECTORY...`, `grep [OPTION]... PATTERNS [FILE]...`. Not one of those forms matched, so every GNU tool without a curated overlay produced a contract with no operands — an agent reading it had no way to name the file to operate on. Both ellipsis placements and the bare all-caps form are now recognised. Two exclusions keep this from over-reporting: `[OPTION]...` and `cut`'s bare `OPTION...` name the option group rather than an operand, and a bracketed group whose first character is `-` is options all the way through — which is what separates `[FILE]` from `[-T]`, `[-Olevel]`, `[-D debugopts]` and BSD's bundled `[-@ABCF]`, where the capitals sit behind a `@` rather than behind the dash. Verified against usage lines read from GNU coreutils 9.7, grep 3.11, diffutils 3.10 and findutils 4.10.0 in the digest-pinned image the overlays' own provenance names.
- **`jq`'s filter — its only required argument — is now extracted.** The usage-line parser required a placeholder name to be a single token, so `jq [options] <jq filter> [file...]` yielded nothing at all and the generated module could not filter anything. Multi-word placeholders are now read (`<jq filter>` → `jq_filter`), and bracketed variadic operands (`[file...]`) are recognised alongside the angle-bracket form. The trailing `...` is required for the bracketed form, which is what stops it from reading `[options]`, `[-l]` or `[--color=when]` as operands — the same restriction the BSD parser has always carried. Both styles are returned in usage-line order, since order is the argument's meaning.
- **Subcommand modules ran the tool name twice (`git git log`).** ([#17](https://github.com/aiperceivable/apexe/issues/17)) The target was built by prefixing the binary path onto `full_command`, which already carries the tool name, so `cli.git.log` emitted `exec:///usr/bin/git git log` and every call came back with `git: 'git' is not a git command`. It affected **every tool that has subcommands** — all 142 `cli.git.*` and all 12 `cli.cargo.*` modules on the reporter's machine. The target is now built from the subcommand path alone. The old shape was pinned as correct by a unit test asserting `"exec:///usr/bin/mytool mytool list"`, forty-six lines above another test whose comment reads *"Root-only target should NOT repeat the tool name as an argument"* — the duplication was recognised on one branch and asserted on the other, which is how it survived the release. That assertion is corrected, and the new coverage executes the module rather than comparing strings: a target that renders is not a target that runs.
- **Hyphenated `module_id`s were written, counted, and then silently dropped.** ([#19](https://github.com/aiperceivable/apexe/issues/19)) apcore enforces `^[a-z][a-z0-9_]*(\.[a-z][a-z0-9_]*)*$` at *registration*, but ids were derived straight from the command name, so `git cat-file` produced `cli.git.cat-file`. `apexe scan` wrote it, `apexe list` reported "142 module(s) found", and the server then refused it with a warning on stderr — **63 of git's 142 subcommands (44%) never reached a client**, and nothing on the success path said so. The charset is now applied at generation time, so the surface a scan reports and the surface a server serves are the same set. The mapping is lossy and one-way, so the real command name is preserved in `metadata["command_path"]` — the hyphen is what argv needs. A unit test asserting that Unicode names survive *into* the id was pinning the same defect (`cli.café.état` is exactly as unregistrable) and now asserts the id is registrable and the name is preserved beside it.
- **Subcommand contracts described the wrong command.** ([#18](https://github.com/aiperceivable/apexe/issues/18)) `git log --help` does not print help — it runs `man git-log`. No Tier 1 parser recognised that shape, so the parse yielded nothing and the module was assembled from the *tool's* global flags alone: all 25 of `cli.git.log`'s properties were `--git-dir`, `--paginate`, `--html-path` and friends, and `{"oneline": true}` was rejected as invalid input. A new `Man` parser reads the man-page layout at Tier 1 using the machinery Tier 2 already had, so a subcommand finally describes itself: `cli.git.log` now carries **111 properties including `--oneline`, `--follow` and `--max-count`**, plus the `<revision-range>` and `<path>` operands recovered from the SYNOPSIS, which were previously inexpressible. Four classes of malformed property name are fixed with it, all of which produced keys no caller could render back to a flag: `--exec-path[=<path>]` yielded `exec_path[`, `--[no-]verify` yielded `[no_]verify`, `-n<num>` yielded `n<num>`, and the end-of-options marker `--` yielded a property whose key was the empty string. A real scan of git now produces **zero unregistrable ids and zero malformed property names** across all 142 modules. The bracket that marks an optional value is recorded rather than discarded, since it is the only thing distinguishing `--exec-path` from `--exec-path=<p>`, and such a flag's schema now admits both spellings.
- **Options that take a value were typed `boolean`, and swallowed the next flag.** ([#21](https://github.com/aiperceivable/apexe/issues/21)) When a placeholder was spelled in a form the format's regex did not anticipate — `--proxy [protocol://]host[:port]`, or a value separated from its description by one space rather than two — it fell into the description text and the flag was typed boolean. Both doors were then shut: the schema permitted only `true`, and `true` rendered a bare flag the binary rejects. Worse, a bare value-taking flag is not a no-op — `{"proxy": true, "connect_timeout": true}` rendered `--proxy --connect-timeout` and curl dialled a proxy named `--connect-timeout`, which is the same "it runs, and honours something the caller never meant" failure `x-apexe-conflicts-with` exists to prevent, reached from the renderer's own output. Affected **11 of `cli.curl`'s 257 properties and 3 of `cli.ssh`'s 45**, including every form of ssh port forwarding. A placeholder left at the head of a description is now recovered and the property retyped, in a pass shared by every parser rather than fixed one regex at a time. The renderer additionally refuses to emit a bare token for an option the schema says takes a value.
- **`find`'s predicates rendered before the path, which no `find` accepts.** ([#20](https://github.com/aiperceivable/apexe/issues/20)) Operands were emitted after every flag unconditionally. `find`'s grammar is `find path ... [expression]`, so `find -name '*.txt' dir` is rejected outright — "illegal option -- n" on BSD, "paths must precede expression" on GNU — making **all 98 predicate properties of `cli.find` unusable**. Operands now carry a placement marker (`x-apexe-operand-position`), and each side of the flags keeps its own declared order, since `find` has one operand on each side. Placement is not derivable from a scan: the usage line gives the operand order but never says which of a tool's options live inside the trailing operand slot — find's predicates are documented in PRIMARIES, not in the synopsis — so it is stated in an overlay or not at all, and a tool without one keeps the ordinary trailing-operand behaviour. Set on `find@bsd` and `find@gnu`, both checked behaviourally against the real binaries (macOS 26.3 `/usr/bin/find`, and findutils 4.10.0 in the digest-pinned image `find@gnu`'s own provenance names).
- **The circuit breaker counted caller mistakes as module failures.** ([#22](https://github.com/aiperceivable/apexe/issues/22)) apcore's breaker feeds every `ModuleError` into its rolling window, which inverts the polarity for a module wrapping a CLI binary: five calls rejected by *input validation* — the binary never spawned — opened `cli.ls` for every caller, while five calls where `ls` really did fail on a missing path left it closed, because a non-zero exit is a successful execution. So a tool that failed every time kept its circuit closed while a caller sending a schema-invalid object disabled it for everyone. That collides directly with apexe's audience: schema trial-and-error is the normal behaviour of an LLM caller, and an agent that reads a conflict refusal and corrects itself is the *success* case for the `conflicts_with` enforcement added in this same release. Only failures that say something about the dependency's health — spawn failure, timeout, signal death — now feed the breaker. Governance refusals are excluded too, so a denied caller cannot open a circuit shared with the callers an ACL allows.
- **`documentation` embedded raw man-page overstrike sequences.** ([#23](https://github.com/aiperceivable/apexe/issues/23)) Help text captured from a tool that delegates `--help` to its man page was stored verbatim, so each `cli.git.*` binding carried `g\bgi\bit\bt l\blo\bog\bg` where it meant `git log` — **2.4 MB for a single git scan**, largely encoding, and unreadable as documentation for the agent that reads it. Overstrike is now collapsed at the point of capture.

### Changed

- **Existing bindings keep working, but need a rescan to benefit.** Every schema keyword introduced in this release is optional, and its absence preserves the prior behaviour: the renderer falls back to the old `--{key}` spelling for any property without the new annotations, so bindings generated before this release behave exactly as they did rather than silently emitting nothing. Re-run `apexe scan` to pick up the corrected flag forms, targets, registrable ids, subcommand contracts and operand ordering.
- **`ln` is annotated `destructive`.** `ln -f` unlinks an existing target before linking, discarding that file's directory entry irrecoverably — the same overwrite behaviour for which `cp` and `mv` are already marked destructive, and the reason GNU `ln` offers `--backup`. Verified against the binary rather than inferred.
- **A man-page placeholder now types the value it names.** `--max-count=<number>` was typed `string`, so the `3` a caller naturally sends was rejected. Inference is deliberately narrow — an unrecognised placeholder stays a string, because a wrong numeric guess rejects a value the tool accepts.

### Fixed (overlays)

- **`ls@gnu`: `-F` / `--classify` takes an optional value.** It was typed `boolean`, so `ls --classify=never` could not be expressed at all under `mode: authoritative`. GNU coreutils 9.7 spells it `--classify[=WHEN]` and rejects `--classify=bogus`; it is now an `enum` over `always`/`auto`/`never`, matching how the same file already handles `--color` and `--hyperlink`. Verified in the digest-pinned image the overlay's own provenance names.
- **`ls@gnu`: `-f`, `-c` and `-u` described behaviour coreutils 9.7 does not have.** `-f` was documented as `disable -ls --color`, which stopped being true years before the 9.7 the overlay claims to describe: `ls -l -f` produces a full long listing and `ls -f -s` prints block counts. GNU 9.7 says only `same as -a -U`. `-c` and `-u` were flattened to `Sort by, and with -l show, ctime` — but the real behaviour is three-way, and the flattened form asserts the opposite of one branch: `ls -lc` sorts **by name**, not by ctime (only `-lt` sorts by it). All three now carry GNU 9.7's own wording, verified against the binary.
- **`find@gnu`: `-prune` was described as false under `-depth`.** It said `Always true unless -depth is in effect`; GNU's man page says `True; ... If -depth is given, then -prune has no effect`, and `find /p/sub -depth -name sub -prune -print` does print, proving the predicate still evaluates true. An agent reading the old text would invert the short-circuit in the standard `-prune -o -print` idiom.
- **`diff@gnu`: `--forward-ed` had its ordering backwards.** It claimed output `in the ed command order, which ed cannot itself digest`. Per diffutils' own manual the forward form carries changes *in the order they appear in the file*; it is `-e`, the form ed *can* digest, that is reversed. The old phrasing was also a reworded BSD man-page line.
- **`sort`: an unattributable claim, present in two variants.** Both `sort@gnu` and `sort@apple` ended `--output` with `The file is truncated and rewritten.` — a sentence in no GNU help, man page or texinfo, and in no macOS man page either. It also implies the opposite of a documented guarantee: sort reads all input before opening the output file, so `sort -o F F` sorts in place, which both variants do. Replaced on the GNU side with the texinfo fact, dropped on the Apple side.
- **`grep@gnu`: `--colour` carried BSD's wording.** `The same as --color` is BSD grep's man page; GNU's help lists `--color[=WHEN], --colour[=WHEN]` as a single entry and never says it.
- **`cp@gnu`, `mv@gnu`, `ls@gnu`: optional values are now stated consistently.** `--backup`, `--preserve`, `--reflink`, `--context`, `--classify` and `--hyperlink` all take an optional value, and only some said so — `cp --context` and `mkdir --context` are the same flag with the same GNU help text, and one documented it while the other did not. `ls --hyperlink` additionally read `Hyperlink file names.`, dropping the `WHEN` its own `value_name` and `enum_values` declared.
- **`chmod@bsd`: `mode` is not always required.** BSD `chmod`'s second usage form — `chmod [-fhv] [-R [-H | -L | -P]] [-E | -C | -N | -i | -I] file ...` — takes an ACL option in place of a mode operand, and `chmod -C <file>` parses fine without one. Marking it required blocked the entire ACL usage form.

### Added

- **`conflicts_with` reaches the generated contract, and a conflicting call is refused.** The field that `docs/overlays.md` calls the single biggest reason overlays exist had no consumer: 42 built-in overlays declare mutual exclusion on 220 flags, and `build_input_schema` never emitted any of it, so not one reached a binding. It is now written to each property as `x-apexe-conflicts-with` — translated from command-line spellings into the property names a caller actually sends — and the executor refuses an invocation that names both.

  Refusing matters more than reporting. Without it the pair is not an error but something worse: it renders, and *which* of the two the tool honours is decided by the order the caller happened to write the JSON keys in. An object has no ordering anyone intended as an interface, so `{"f": true, "i": true}` on `rm` was never "interactive wins" — it was whichever key was typed last. The call now fails with a message naming both flags, identically whichever order they arrived in.

  `false` and null still render nothing and so do not count as sending a flag: `{"l": true, "1": false}` remains a valid way to say "long listing, not single-column". Only curated overlays state mutual exclusion, so a schema without the annotation is unaffected.

### Changed (overlay format)

- **175 mutual-exclusion pairs added across 22 overlays.** Once the definition widened and the executor began enforcing it, the overlays that had recorded only diagnosed errors were left with real gaps — a group the binary resolves silently is exactly the one a caller cannot predict, so it is the *more* important of the two to declare. Every pair was run in both orders against the reference build named in that overlay's own provenance (BSD/apple on macOS, GNU in the digest-pinned image) and kept only where the outcome depends on that order, or where one side is silently discarded. Biggest gaps: `ls@gnu` +45 (sorting, timestamp source, quoting style, indicator style, size units — seven separate dimensions, of which only output format had been recorded), `df@bsd` +22 (the seven-way block-size group its SYNOPSIS spells with `|`), `grep@gnu` +15 and `grep@bsd` +11 (output modes had been declared against `-n` but never against each other), `du@gnu` +13, `df@gnu` +10, `diff@gnu` +10 (`-q`/`--brief` overrides every output style silently, which is why it escaped the group everything else was diagnosed into).

  Same-named flags diverge between variants more than expected, and each side was derived only from its own evidence: `wc -c -m` overrides on BSD but prints both columns on GNU; `uniq -d -u` lets `-d` win outright on BSD while GNU yields the empty set identically in either order; `rm -i -I` coexists on BSD but is last-one-wins on GNU; `sort -c -m` is diagnosed by Apple's build and accepted by GNU's, and `-c -o` the other way round. Four pairs were tested and deliberately *not* declared, since a wrong entry now refuses a legal call: `tail@bsd -f/-F` (`-F` implies `-f`), `grep -o/-n` (both take effect), `rm@bsd -i/-I` (both prompts fire), `df@gnu -P` (not part of the block-size dimension). The `provenance.notes` in every touched file record which kind each group is, and sentences written under the older narrow reading were corrected rather than left to contradict the data.
- **`conflicts_with` covers override groups, not only diagnosed errors.** The 42 built-in overlays had been split between the two readings, so the same field meant different things in different files. It now means "these must not be sent together" in both senses, and the reason is specific to how apexe is called: its input is a JSON object, which has no ordering, so for a last-one-wins group *which* flag wins is decided by the order the caller happened to write the keys in. `{"f": true, "i": true}` on `rm` is not "`-i` wins", it is unpredictable — the same one correct move as for a hard conflict, namely send one or the other. The narrower reading is actively worse here: it marks such a pair as combinable, which tells an agent it may send both. `du@bsd`'s note, which had stated the opposite rule, is corrected; `provenance.notes` is now where the *kind* of incompatibility is recorded.
- **`provenance.source` is documented as the document read, not the check performed.** No `binary-probe` value was added, and the reasoning is written down so it is not revisited by guess: probing establishes that a flag exists, what the binary prints on rejection, and whether a value must be attached — but not what a flag *means*, which is what a description asserts and what `source` attributes. `ls@gnu`'s `-f` is the case in point: `--help` was right the whole time and the description was stale, so the probe's role was to send someone back to the document. Probe findings belong in `notes`, with the command that produced them.

### Documentation

- The built-in GNU overlay count in `docs/overlays.md` said 14; there are 21, and four of them declare `GNU diffutils` / `GNU grep` / `GNU findutils` rather than `GNU coreutils`.
- **Every `provenance.command` that names a container image now pins it by digest.** Twenty GNU overlays ran `docker run --rm debian:stable-slim <tool> --help` while their `environment` pinned a digest — a self-contradiction that would have re-read a different build on any later run. `docs/overlays.md` now says so explicitly, since it already required a digest for `environment`.
- The basic example advertised flag counts that no longer matched what a scan produces (`curl — 12 flags`, against 257 actually found) and suggested a `cli.curl` call with no `url`, which cannot succeed. Its sample calls now run, and it states that Explorer prefills every schema property as a blank template that has to be trimmed before calling — an empty string is a value, not an omission, and `curl --output ""` fails on it.

### Fixed (self-review of the above)

Seven defects the fixes above introduced, each found by reviewing this release
against real binaries and each verified by re-running the failing case. They are
listed separately because every one of them is a regression created by a fix in
this same release, not a pre-existing bug.

- **The circuit breaker's error filter disabled a module in the half-open state.** Not counting a caller-fault error is not the same as the call never happening. In `HALF_OPEN` apcore admits exactly one probe and releases the slot in only two places — `after` on success, and the `on_error`-that-opens branch, which in that state is *every* `on_error`. Returning early therefore skipped the only release path the call had, and because apcore runs middleware `before` *ahead of* input validation, one invalid argument object was admitted as the probe and then rejected, leaving the slot held. Every other caller was refused with `CircuitBreakerOpen` for a full 30-second recovery window: the exact defect #22 exists to remove, relocated from `CLOSED` into `HALF_OPEN`. The suppressed path now hands the slot back, leaving the rolling window untouched so a caller mistake still cannot launder an unhealthy dependency back to `CLOSED`.
- **Operand placement broke `find`'s options while fixing its predicates.** `find` puts two classes of dash-token on opposite sides of the same operand — options before the paths, primaries after — and `before_flags` is a single boolean on the operand, so it moved both at once. `find dir -L` is "unknown primary or operator" on BSD and "unknown predicate" on GNU, so 8 BSD and 6 GNU properties went from working to broken while the 88 primaries went the other way. Placement is now expressible per flag as well (`before_operands` → `x-apexe-flag-position`), and the renderer emits four ordered groups: leading flags, leading operands, trailing flags, trailing operands. Each of the 14 options was run in both positions against the builds the two overlays' provenance names; `-d` was tested and deliberately left unmarked, because BSD accepts it either way.
- **`apexe scan --format json` reported command lines that do not run.** The id fold is one-way, and `CommandContract.command` still reverse-derived from the id, so **68 of git's 142 commands** were reported as `git check_ignore`, `git cherry_pick`, `git format_patch` — strings git rejects. `metadata["command_path"]`, added in this release precisely to hold the unfolded name, had no reader. The field is now built from it, falling back to the id only for bindings written before that key existed.
- **The placeholder-recovery pass re-typed working boolean switches.** It accepted any first token containing brackets and any ALL-CAPS first word, neither of which is reliably a placeholder: Info-ZIP prefixes **16 boolean switches** with `[WIN32]` / `[VMS]` / `[MacOS]`, `[deprecated]` is a widespread convention, and descriptions open with a caps identifier (`ld -noprebind` — "LD_PREBIND is no longer supported"; `ex --echo-wid` — "GTK GUI only:"). Each became a value-taking string option that could no longer be sent as `true` at all — the inverse of the bug the pass was written for. The bracket form now requires text *outside* the brackets, which is what distinguishes `[protocol://]host[:port]` from a tag, and the bare-caps form is restricted to a closed list of conventional operand words.
- **`--time-cond` was typed as a number.** `contains("time")` matched as a substring, so curl's `-z, --time-cond <time>` — which takes a date expression or a filename — admitted only values curl cannot use. Durations are now matched as whole words.
- **The end-of-options fix did not actually drop the flag.** `parse_flag_line` skipped *naming* a bare `--` but still returned a flag, so it reached the schema through `canonical_name`'s `"unknown"` fallback: **6 of git's 142 modules** advertised a boolean property named `unknown` that renders as `--unknown`, which git rejects. Nameless flags are now dropped at the single point every parser path funnels through. The regression test passed throughout because it asserted the name was non-empty, which the fallback satisfies; it now asserts the count.
- **Man-page synopses leaked option letters and option values as operands.** A synopsis spells an alias set as a parenthesised alternation — `[(-m | --max-count) <num>]` — so the character after `[` is `(` rather than `-` and the group read as operands, and the check ran only on the innermost bracket. `cli.git.grep` declared `o`, `pager` and `num` as positionals, and on `cli.git.commit` an operand named `c` **displaced git's real `-c` option**, making it unreachable. The option-group check now skips a leading `(` and walks outward through every enclosing group, and the angle-bracket pass consults it at all — which it never had, because ordinary `--help` text writes `[-C <path>]` and never exposed the gap.

A rescan of git now produces 142 modules with zero unregistrable ids, zero malformed property names, zero bogus `unknown` properties, zero non-invocable command strings, and `-c` restored as a flag.

### Changed (self-review of the above)

Eight further findings from the same review. None is a wrong answer to a caller,
so they are listed apart from the defects above.

- **An existing cache silently bypassed every scanner fix.** The cache key named only the tool, variant and version, so it did not change when apexe's own parsing did — and because every field added to the scanned model is `#[serde(default)]`, a document written by an older build still deserialized and was returned before any parsing ran. A user who upgraded and re-ran `apexe scan git` got the pre-fix result at exit 0 with nothing saying so, and `--no-cache` was the only escape. The key now carries a `SCAN_FORMAT_VERSION`, bumped to 2 for this release.
- **A positional operand no longer erases a same-named flag.** "Operand wins" is right for `curl`, where `--url` and `<url>` are the same thing, but `find -path PATTERN` is a glob predicate unrelated to the `path` operand, and `grep --file=FILE` reads patterns from a file while the `file` operand names what to search. Both options had vanished from their contracts entirely. The displaced flag is now re-keyed (`path_option`, `file_option`) rather than dropped; the executor spells a flag from `x-apexe-flag`, never from the property key, so the rendered command line is unchanged.
- **Accurate subcommand summaries are no longer padded with the parent tool's description.** Appending the tool's man DESCRIPTION to any subcommand summary shorter than 20 characters made sense while those summaries were stubs. Once the man parser started supplying real NAME lines, `git log` → "Show commit logs" became "Show commit logs — Git is a fast, scalable, distributed revision control system…", 84% of which describes `git` — the same "description of git filed under the name of git log" the man parser exists to prevent. A summary that came from a man page is now left alone.
- **Scanning by absolute path yields the same contract as scanning by name.** `ManHelpParser` forwarded the raw `tool_name` to example extraction, which matches a bare invocation by prefix — so `/usr/bin/git` matched no EXAMPLES line and the same tool produced different output depending on how it was named.
- **One placeholder-to-type table instead of four.** `parsers::gnu`, `parsers::clap_parser`, `parsers::click` and the new recovery pass each carried their own, and they disagreed: `SIZE` was String in one and Integer in another, `FLOAT`/`DECIMAL` existed only in the GNU copy, durations only in the new one. Both the help path and the man path feed the same merged flag list, so an option's emitted JSON type depended on which parser happened to win on that host — `{"size": 4096}` validated against one machine's contract and was rejected by another's.
- **The circular dependency between `scanner::man_page` and `scanner::parsers` is gone.** `value_placeholder` is a post-parse repair pass with consumers on both sides of the tier boundary, not a `CliParser`, so it now lives at `scanner::value_placeholder`.
- **`value_optional` is declarable and documented.** It reached the Rust overlay loader and the emitted contract but never `$defs/flag` in `schemas/tool-overlay.schema.json`, which is `additionalProperties: false` — so an author writing it got a validation failure for a field the loader honours, and the field appeared in no document. Both are fixed, and `before_operands` was added to the schema alongside it.
- **BREAKING (library): one unscannable tool no longer discards the whole batch.** `ScanOrchestrator::scan` propagated the first error with `?`, so `apexe scan git curl nonexistent` wrote *no* bindings at all — the tools already scanned were thrown away, the tools after it were never reached, and the message named no tool. Scanning is per-tool work with no shared state, so there was nothing to abort for. It now returns a `ScanOutcome { tools, failures }` instead of `Result<Vec<_>>`; each failure carries the tool as the caller named it and the rendered cause. The CLI writes bindings for everything that scanned, names every failure, and still exits non-zero — reporting `Scanned 21 of 22 tools` with the successes on disk, because a pipeline must not read a short surface as the whole surface. A run where *nothing* scanned fails outright and writes nothing, since an empty ACL over a good one is worse than doing nothing.
- **Array-typed paths and URLs carry their `format` hint again.** The hint exists so an agent can tell a path from free text, but it was attached inside the scalar branch of each schema builder, so both array branches dropped it — and arrays are the common case for exactly those types. Scanning ten of the overlay-backed tools recovers 12 hints that were previously emitted for none of them. It is attached to `items`, where it describes each element rather than the array, and `format_hint` is now the one place that decides it.
- **Documentation that this release invalidated.** The parser inventory was stated in four places and only `FEATURE_MANIFEST.md` was guarded, so the user manual still said "Five", and the README and the scanner's crate doc still listed the four parsers from before BSD Usage existed. §9.5 of the manual still described `CircuitBreakerMiddleware` counting every failure — the behaviour this release removes. All four sites are corrected and the doc-consistency test now covers the manual, the README and the crate doc, so the next parser cannot go stale in one file only.


### Known gaps

- **The negated half of `--[no-]verify` is not listed separately.** The notation documents both `--verify` and `--no-verify`; the parser emits one flag per option line, and the affirmative form is what it keeps. Manufacturing the second flag is a change to that contract rather than a fix to a malformed name, so it is left for its own change.

## [0.5.1] - 2026-07-28

### Fixed
- **A global option's value placeholder is no longer scanned as a positional argument.** Usage lines spell an option's argument with the same `<name>` angle brackets as a real operand, and the extractor took every `<name>` on the line — so `usage: git [-v | --version] [-h | --help] [-C <path>] [-c <name>=<value>]` gave `git` three *required* positional arguments named `path`, `name` and `value`, none of which the bare command accepts. An agent reading that contract would construct a call `git` rejects. Placeholders bound to an option (`-C <path>`, `-c <name>=<value>`, `--git-dir=<path>`, `--exec-path[=<path>]`, and repeatable forms like `--include=<path>...` and `-I <dir>...`) are now skipped, and a placeholder inside an optional `[...]` group reports `required: false` instead of the hardcoded `true` — the trailing `<args>` in `git [--version] <command> [<args>]` is optional by construction.
- **The four help parsers share one usage-line extractor.** `gnu`, `cobra`, `clap` and `click` each carried a verbatim copy of the same naive regex, so the defect was present in all of them and a fix to one would have left three behind. They now call `scanner::parsers::positional_args::extract_args_from_usage_line`. The BSD parser already avoided this class of mistake (its `BUNDLED_RE` documents why valued options must not match) and is unchanged. Overlays are unaffected — they carry no subcommand layer and never took this path.

## [0.5.0] - 2026-07-28

### Added
- **Man page `EXAMPLES` are extracted** — `ScannedCLITool.examples` and `CommandContract.examples` now carry the hand-written invocations from a tool's man page: `ls` yields 3, `find` 9, `tar` 10 and `grep` 13, where every tool previously yielded 0. This is the only human-reviewed usage a scan can reach — help text lists what the flags *are*, while `EXAMPLES` shows which combinations make sense together, and no amount of flag parsing recovers that. Both man layouts are matched: a shell prompt (`$ grep -w 'patricia' myfile`, used by `ls` and `grep`) and a bare invocation (`tar -czf file.tar.gz source.c`, used by `tar` and `find`). A bare invocation is accepted only when it starts with the tool's own name, which is what separates a command from the prose describing it — every one of these pages interleaves the two. Kept as command lines rather than parsed into structured inputs, deliberately: `find / \! -name "*.c" -print` does not survive being parsed back into schema fields, and a consumer that guessed at one would emit a call the tool rejects.
- **`CommandContract.examples`** — the flattened contract dropped the examples the generated binding carried, so one scan described the same command differently depending on which output a consumer read.
- **Prebuilt release binaries** — a GitHub Actions workflow (`.github/workflows/release.yml`) now builds `apexe` for `x86_64`/`aarch64` on both macOS and Linux and attaches the archives (plus `sha256` checksums) to the GitHub Release, so installing no longer requires a Rust toolchain. It runs on the `rust/v*` tag that `apdev-rs release` pushes, or can be dispatched manually against an existing tag to backfill binaries. `aarch64-unknown-linux-gnu` builds natively on GitHub's `ubuntu-24.04-arm` runner rather than cross-compiling, avoiding a `pkg-config` cross-compilation sysroot that isn't set up on the `x86_64` runners.

### Changed
- **Linux release builds statically link OpenSSL** — `Cargo.toml` now pulls in `openssl` with the `vendored` feature for `cfg(target_os = "linux")`, so the released Linux binaries no longer depend on whatever OpenSSL version happens to be installed on the end user's distro.

### Fixed
- **BREAKING: `open_world` is inferred rather than asserted.** It was hardcoded `true` for every command, which left the annotation carrying no signal at all: `ls` and `curl` were indistinguishable, `risk_from_annotations` had to ignore the field (its own doc comment said so), and **`Risk::OpenWorld` was therefore never emitted by any scan** — a declared risk class no output could contain. A consumer gating on the boundary (demanding a declared credential, or refusing to run a networked command in a local sandbox) had nothing to gate on. Two signals now: the executable itself (`curl`, `wget`, `ssh`, `scp`, `sftp`, `rsync`, `nc`, `telnet`, `ftp`, …), and networked subcommands of otherwise local tools (`push`, `pull`, `fetch`, `clone`, `publish`, `install`, `deploy`, `login`, …). `git` scans to 4 `open-world`, 7 `readonly`, 127 `write` and 4 `destructive` commands where every one was previously alike. Name-based, so it is a floor rather than a guarantee — a tool that opens a socket under an unremarkable name is not caught, and an overlay's `annotation_overrides` remains the way to state the truth for a specific one.
- **BREAKING: `risk` consumes `open_world`.** `curl`, `wget` and `ssh` report `open-world` where they reported `write`. Destructive outranks open-world, because irreversibility is what a consumer must gate on first; open-world outranks readonly, because `curl` reading a URL still crosses a trust boundary, and reporting it as readonly hides it from the gate that exists for exactly that.
- **`--format` and `-j` no longer imply JSON output.** The structured-output regex fallback matched a bare `--format` or `-j` anywhere in help text, so `tar` was tagged `structured-output` — telling an agent it could request JSON from a command that has never emitted any. `tar --format` selects an archive format (`ustar`, `pax`, `cpio`) and `tar -j` selects bzip2 compression. Every pattern now requires the word `json` on the same line as the flag, which keeps the Cobra-style `--format string   Output format (json, text)` matching while dropping `tar`'s bare `--format <format>`. `-j` is removed entirely: across CLIs it means "jobs" or "bzip2" far more often than JSON.

## [0.4.0] - 2026-07-28

### Added
- **Tool variant detection** — a command name does not identify a program, so every scan probes the binary (`<binary> --version`) and classifies it as `bsd`, `gnu`, `apple`, `busybox` or `unknown`, surfaced as `ScannedCLITool.variant`. macOS `/bin/ls` is BSD, Linux `/usr/bin/ls` is GNU coreutils, Alpine is BusyBox, and Homebrew coreutils puts GNU `ls` on a macOS box — the probe is the only signal that separates that last case from the system binary, so no path heuristic can replace it. `gnu` spans the whole GNU family rather than coreutils alone, since `diffutils`, `tar`, `sed` and `bash` are separate projects; `apple` covers Apple's own ports, whose banner names Apple rather than BSD (`sort` reports `2.3-Apple (197)`, `git` reports `(Apple Git-155)`).
- **The classification order is fixed and load bearing.** Six rules run in sequence: `busybox`, a BSD marker, a `GNU <package>` pair, an Apple marker, a rejected `--version` corroborated by a BSD-family platform, then `unknown`. **BSD is tested before GNU** because macOS `grep` reports `grep (BSD grep, GNU compatible) 2.6.0-FreeBSD` — a BSD tool advertising GNU compatibility, not a GNU tool. The Apple rule strips `<arch>-apple-<os>` target triples first, since `curl 8.7.1 (x86_64-apple-darwin25.0)` and `GNU bash ... (arm64-apple-darwin25)` both carry the token without being Apple ports. Licence boilerplate is excluded from the GNU test, because every GPL tool prints `GNU General Public License` whether or not it is a GNU project. A `bsd` verdict from a *rejected* probe additionally requires platform corroboration: rejecting `--version` only proves a tool is not GNU. BSD markers match token *prefixes*, so `bsdtar 3.5.3 - libarchive` classifies as BSD. The reasoning is recorded in `docs/overlays.md` so the order is not "simplified" later.
- **Curated tool overlays** — a reviewed description of one variant of one command, keyed by `(command, variant, version_range)` and matched by `probe` > `platform` + `binary_globs` > `platform` alone. `mode: authoritative` replaces the scan surface entirely (for system built-ins the overlay fully enumerates); `mode: merge` keeps the scan as the base and overrides matching flags. Overlays are the only source that can state `conflicts_with`, since no help or man page format expresses mutual exclusion machine-readably. **42 ship built in**, covering the 21-command POSIX core across their BSD, GNU and Apple variants — `cat chmod cp cut df diff du find grep head ln ls mkdir mv rm sort tail touch uniq wc xargs`; `~/.apexe/overlays/*.{json,yaml}` and `apexe scan --overlay <PATH>` add more. The format is defined by a standalone JSON Schema at `schemas/tool-overlay.schema.json`, with tests guarding it against drifting from the Rust types.
- **Overlay provenance is mandatory at `confidence: verified`** — an overlay claiming to be verified must record how it was checked: the platform and version of the reference installation, the upstream `package`, which document was read (`man-page` / `help` / `vendor-docs`), the date, and ideally the re-runnable command and a digest-pinned environment. The schema rejects a `verified` overlay without it, and `vendor-docs` additionally requires a `reference` citation because it has no command anyone can re-run. Without this, a `verified` + `authoritative` overlay replaces the entire scan result with an assertion nobody can re-check. `EvidenceSource` has exactly three variants by design — there is none meaning "I know this tool", because that is not evidence.
- **Per-flag `confidence` and `sources`** — every `ScannedFlag` records which tiers produced it, plus a derived trust level: `verified` (overlay) > `high` (completion spec) > `medium` (two independent heuristic sources agree) > `low` (a single unconfirmed source). Consumers can now tell a curated fact from a text-scraping guess. On macOS, `ls` reports 46 `verified` flags; `curl` reports 12 `medium` and 245 `low`.
- **`ScannedCLITool.positional_args`** — tool-level positional arguments (`ls [file ...]`) now reach the generated input schema through the synthesized root command. Tier 1 parsed them and then discarded them.
- **Overlay behavioral annotations** — an overlay may assert `readonly` / `destructive` / `idempotent` / `requires_approval`, overriding the adapter's name-and-flag inference. Only fields the overlay actually sets are replaced.
- **Man pages promoted to a first-class usage source** — Tier 2 now contributes flags to `global_flags`, not just descriptions to flags Tier 1 already found. Tools whose `--help` is a single bundled usage line (most BSD/macOS built-ins) previously scanned to zero flags: on macOS, `ls` now yields 46 flags (was 0), `grep` 51 (was 0), `git` 25 (was 0), `curl` 257 (was 12).
- **BSD man page layout support** — options listed inside `DESCRIPTION` are parsed, in addition to the GNU `OPTIONS` section. The intro line is matched as a pattern (`the … options are as follows/available`) rather than a fixed list, because the wording varies per page and the variants arrived one bug at a time: `ls` says "The following options are available", `cat` "The options are as follows", `sort` "The command line options are as follows", `chmod` "The generic options are as follows". Missing one is silent — the entire option block simply becomes invisible, which cost `sort` 10 flags and `chmod` 4 before this was generalized. Option indentation is inferred from the first option line instead of being hardcoded to GNU's 7 columns (BSD uses 5).
- **Man page flag detail** — alias lists (`-a, --all`), inline values (`--color=when`), and separate value placeholders (`-D format`, `-o FILE`) are parsed, so value-taking flags map to `string` and switches to `boolean` instead of everything defaulting to `string`.
- **`ScannedCLITool.description`** — tool-level description sourced from the man page `DESCRIPTION`. Subcommand-less tools previously fell back to a bare `Execute <name>`.
- **Empty-scan warning** — a scan that extracts no flags and no subcommands now records a warning instead of silently returning an empty result.
- **`BsdUsageParser`** — fifth built-in parser (priority 95, ahead of GNU) for the single-line bundled usage that BSD/macOS built-ins print when they reject `--help`: `usage: ls [-@ABC...] [--color=when] [-D format] [file ...]`. Expands the bundled group into individual boolean switches, and parses valued short options, long options with inline values, and variadic operands. It claims only text containing a genuine bundled group, so GNU-style help still routes to the GNU parser.
- **git-style subcommand lists** — the GNU parser recognizes prose section intros ("These are common Git commands used in various situations:") in addition to `Commands:` headers, and tolerates command lists split into blank-line-separated labelled groups. `git` previously yielded zero subcommands.
- **`long_running` on an overlay flag** — a machine-readable form of "this option may make the command never terminate on its own". `tail -f` blocked an agent against the harness timeout for a full two minutes during overlay verification, and the only way to say so was prose in a `description`, which no executor can act on. It reaches `ScannedFlag.long_running` and then the emitted contract as the JSON Schema extension keyword `x-apexe-long-running` — an extension rather than a constraint, because `follow: true` is a perfectly valid *value*; what it tells an executor is to bound the timeout or refuse. The claim is **possibility, not certainty**: the BSD man page states `tail -f` returns immediately when its input is a pipe, so a field asserting "always blocks" would be false. Set on exactly four verified flags (BSD `tail -f`/`-F`, GNU `tail -f`/`--follow` and `-F`); flags that merely change how long a follow lasts (GNU `--retry`, `--sleep-interval`, `--pid`, `--max-unchanged-stats`) are deliberately out of scope, since none of them decides termination.
- **`match.platform` is an open string, not an enum** — taken verbatim from `std::env::consts::OS` and normalised to lower case, so `macos`, `linux`, `freebsd`, `openbsd`, `netbsd`, `dragonfly`, `solaris` and anything else a host reports all work without an apexe change. Operating systems are not an enumerable set, and a closed enum would collapse every unnamed one into a lossy `Other` bucket. `ToolVariant` stays an enum for the opposite reason: each member exists only because the classifier can probe for it, and a string would let an overlay declare `variant: "gnu-ish"` and silently never match. There is deliberately no Linux distribution dimension — GNU coreutils `ls` has the same 83 flags on Debian 9.7, Ubuntu 9.4 and Fedora 9.5, while BusyBox `ls` has 21, so divergence tracks the implementation, which `variant` already captures.
- **Single-dash multi-character flags** — an overlay's `short` field accepts `-maxdepth`, `-delete`, `-name`, `-files0-from`. `find`'s entire expression language is built from these, so it was previously inexpressible: validation demanded exactly two characters. A `--long` token misfiled under `short` is still rejected, since validation now checks each field against its own rule rather than walking the merged name list.
- **`docs/overlays.md`** — the overlay authoring guide: when an overlay is warranted, the per-variant verification procedure with exact commands (`man -P cat <tool> | col -b` for BSD, `docker run --rm debian:stable-slim <tool> --help` for GNU, `alpine` for BusyBox), how to fill in provenance, an explicit table of what can and cannot be machine-checked, and the traps already hit in practice.

### Changed
- **Shell completion directories discovered dynamically** — zsh's `$fpath` is queried once per process instead of guessing three hardcoded paths, none of which exist on macOS (system completions live in the version-stamped `/usr/share/zsh/5.9/functions`). Homebrew and distro bash-completion directories are also checked. Tier 3 previously never activated on macOS.
- **Completion subcommand extraction rewritten** — prefers the `_<tool>-<subcommand> ()` function convention that system zsh completions follow; the `commands=(...)` array fallback is now confined to the array body. The previous whole-file scan for `'name:description'` matched `_arguments` option specs, which would have injected phantom subcommands (`_ls` advertises a `formats` spec despite `ls` having no subcommands, and `_git` yielded 131 internal completion tags rather than git's actual commands).
- **BREAKING: `apexe scan --format json|yaml` emits a single `ScanReport` document** — `{ "tools": [...], "commands": [...] }`. Previously each tool was printed as its own document, so a multi-tool scan's stdout was not valid JSON. `commands[]` is a new flattened per-command contract (`id`, `command`, `description`, `risk`, `input_schema`, `output_schema`) for consumers that bind against commands rather than walking the parse tree. Consumers reading the old top-level `ScannedCLITool` shape must now read `tools[0]`.
- **BREAKING: the dormant `user_override` path is gone** — `ParserPipeline::parse` no longer takes `user_override: Option<&Path>`. That hook loaded a `ParsedHelp` YAML document at a layer that cannot see the tool's variant, so it could not express "BSD `ls`, but not the Homebrew GNU one", and `ScanOrchestrator` always passed `None` — it was unreachable. Overriding a scan is now the overlay mechanism's job, reachable via `apexe scan --overlay <PATH>`. An explicitly named overlay outranks every other source and skips the variant, platform and probe conditions it declares; only the command name must still agree, so a mistyped path cannot silently reshape an unrelated tool.
- **Scan cache keyed by variant** — cache entries are now `<name>@<variant>_<version>.scan.json`. A machine holding both BSD `/bin/ls` and Homebrew's GNU `ls` (both reporting no usable version) previously shared one entry, so whichever was scanned last supplied the other's flags.
- **Tool identity normalized to the command name** — `scan /bin/ls` and `scan ls` now produce the same `name`, module id (`cli.ls`), cache entry, and risk annotation; the full path is kept in `binary_path` for execution. Previously an absolute path produced `cli./bin/ls`, skipped man/completion lookup entirely, failed to cache, and mis-inferred risk as `write` instead of `readonly`.

### Fixed
- **Man page parsing was inert on macOS** — `man -P cat` emits nroff overstrike (`D\bD`), so every section header read as `DDEESSCCRRIIPPTTIIOONN` and never matched. Overstrike is now stripped, which is what made Tier 2 reachable at all on BSD systems.
- **Logs no longer corrupt machine-readable stdout** — `tracing` writes to stderr instead of stdout. `scan --format json` interleaved log lines into its own output, so any consumer doing `JSON.parse(stdout)` failed unconditionally.
- **Help error text no longer used as a description** — a tool that rejects `--help` (`ls: unrecognized option '--help'`) had its error message parsed as the tool description; the man page `DESCRIPTION` now takes precedence.
- **`ls@gnu` was missing `--zero`** — found by diffing the overlay against a real GNU coreutils 9.7 `--help` in a container. That overlay had been written without a GNU reference installation: it scored 100% precision but omitted a flag added in coreutils 8.25. Everything present was correct, which is what makes this failure mode hard to notice, and is why provenance is now required.

### Notes
- **No `apexe overlay verify` subcommand was added, deliberately.** A tool can compare flag names; it cannot check descriptions, `conflicts_with`, types or enum values — and those are the reason overlays exist at all. A green check covering only the mechanical half would be read as "this overlay is correct". The verification procedure is documented for humans instead. See "What cannot be automated" in `docs/overlays.md`.

- **Upgraded apcore ecosystem** — `apcore = "0.26"`, `apcore-cli = "0.10"`, `apcore-mcp = "0.17"`, `apcore-toolkit = "0.10"` (`default-features = false`), plus new `apcore-a2a = "0.4"`.
- **`ModuleDescriptor` construction rewritten** — matches the reshaped struct (`module_id`, `description`, `version`, `documentation`, `annotations: Option<...>`, etc.) shared by the new MCP and A2A builders via `crate::module::registry::build_executor`.
- **`output/loader.rs`** — `load_modules_from_dir` now delegates to apcore-toolkit's `BindingLoader` (strict mode) instead of a hand-rolled parser, picking up a 16 MiB per-file cap and a 10,000-file per-directory cap for free. Drops the undocumented bare-single-`ScannedModule`-without-a-`bindings`-key fallback, which `YamlOutput` never produced anyway.
- **Timeout retryability moved from `execute_subprocess` to `CliModule::execute`** — a killed subprocess may have partially applied a non-idempotent side effect, so only `CliModule` (which knows the module's `idempotent` annotation) decides whether a timeout is safe to retry.
- **Removed the non-functional `apexe a2a --enable-approval` flag** — A2A has no elicitation transport and no CLI approval-store, so the flag could only ever error at serve time. Approval on A2A remains a library-only feature (supply an `ApprovalStore`); `apexe serve --enable-approval` is unaffected.
- **Parser regexes compiled once (`LazyLock`)** — help-format parsers hoisted per-call `Regex::new` to module-level statics, removing thousands of recompiles on deep subcommand trees.
- **CRLF help normalized at the parser pipeline boundary** — `\r\n`/`\r` help text (e.g. a Windows tool's output) now parses identically to `\n` across all parsers.
- **Specs aligned to implementation** — the F5 `--sandbox`/`SandboxManager` and F4 `--require-auth` designs are removed from the feature specs; subprocess isolation is unconditional (see Security) and transport auth is delegated to the apcore library API with a localhost default.

### Removed
- **`SandboxManager` / `governance::sandbox`** — deleted. `apcore-cli::Sandbox` requires the host binary to re-exec itself with an `--internal-sandbox-runner` subcommand and rediscover modules from `APCORE_EXTENSIONS_ROOT`; apexe's runtime-scanned `CliModule`s don't fit that model. There is no `--sandbox` toggle: subprocess isolation (timeout + kill-on-drop, output caps, no-shell direct argv, **environment scrubbing**) is applied unconditionally in `execute_subprocess`.
- **`nom` dependency** — the unused nom-based `parse_flag_line` GNU parser (~130 LOC, never wired into the parse path) was deleted; GNU help extraction uses regex only.

### Security
- **Environment scrubbing for wrapped subprocesses** — an agent-invoked CLI no longer inherits apexe's full process environment. `execute_subprocess` clears the env and passes only a base allowlist (`PATH`/`HOME`/`USER`/`LOGNAME`/`SHELL`/`LANG`/`LC_*`/`TERM`/`TZ`/`TMPDIR`), so secrets in apexe's environment (API tokens, cloud credentials) cannot leak to a wrapped tool. File-based credentials under `$HOME` still work.
- **ACL fails closed** — `apexe serve`/`apexe a2a --acl <path>` with a missing or malformed file now refuses to start, instead of logging a warning and serving with **no** access control (which apcore treats as allow-all).
- **Audit log hardened to `0o600`** — the JSONL audit log (executions + ACL decisions) is created owner-only, so caller identities and denied targets are not world-readable on shared hosts.

### Fixed
- **`ErrorCode::AclDenied` → `ACLDenied`** rename tracked.
- **ACL audit logger now populated** — the served ACL is built with an audit logger wired to `AuditManager` (previously constructed with `None`), so allow/deny decisions are actually recorded.
- **`apexe scan`/`apexe list` surface failures** — `scan` exits non-zero when a binding/ACL/skill write fails (was warn-and-exit-0); `list` surfaces a corrupt binding's parse error instead of a misleading "No modules found".
- **Resolved `log_level` applied to logging** — `APEXE_LOG_LEVEL` / `config.yaml` `log_level` now feed the tracing subscriber (precedence `RUST_LOG > --log-level > config > "info"`); previously only `--log-level`/`RUST_LOG` took effect.
- **Adapter propagates examples & deduplicates module ids** — scanned `command.examples` now reach the generated module; colliding `module_id`s after subcommand flattening are disambiguated; the output schema advertises `json_output` only when the structured format is JSON.
- **Scanner robustness** — every scan subprocess is timeout-bounded (was only the top-level `--help`); the shared timeout helper drains stdout/stderr concurrently to avoid a deadlock on large output; a discovered subcommand's `help_format` is tagged from the matching parser (was hardcoded `Unknown`); `cache.invalidate()` matches the exact tool name (was an over-broad prefix); the cobra parser handles CRLF section boundaries.
- **Failed/killed executions are audited** — a timed-out or spawn-failed run records a `status=error` audit entry instead of leaving no trace.
