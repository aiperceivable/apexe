## [Unreleased]

### Added

- **An overlay can carry a `$schema` line, and the format now documents itself for consumers other than apexe.** `ToolOverlay` sets `deny_unknown_fields` and the standalone schema sets `additionalProperties: false`, so the one line every editor looks for — `"$schema": "…"` — made a file fail to load outright with `unknown field \`$schema\``. A format that cannot point at its own definition is a hard thing to hand to an outside implementer, which is what this release starts doing. The field is read by tooling and by nothing else: the loader neither fetches nor validates against it (`validate_overlay` is hand-written Rust, not a JSON Schema check), a file naming some other schema still loads, and the line round-trips so a rewritten overlay keeps it. Both halves are tested, because the schema refusing what the loader accepts is the same defect in the other direction.

  **`mode` and `confidence` are described in terms of the data rather than apexe's scanner.** `mode` said "replaces the *scan result*" — true of apexe and meaningless to anyone else; the underlying assertion is *complete enumeration* versus *partial patch*, which any consumer holding a weaker description of the same command can act on. `confidence` named a trust level without saying what earns it; the four levels are now defined by the evidence behind them (`verified` = read off the running tool with a re-runnable check recorded, down to `low` = one unconfirmed source), with the note that they describe evidence rather than the author's certainty — writing from knowledge of a tool is `low` however sure the author is. No field changed shape and all 44 shipped overlays still validate.

  **New: [`docs/overlay-consumers.md`](docs/overlay-consumers.md).** The reading half of `docs/overlays.md`, and the knowledge that until now existed only in apexe's source: how `match` is evaluated and why a declared-but-failing `probe` rejects an overlay outright rather than degrading to a path match, what `authoritative` obliges a consumer to discard, and the four fields that decide an `argv` — `value_optional` (attached spelling only), `conflicts_with` (unordered input has no last-one-wins), `before_operands`/`before_flags` (find puts two classes of dash-token on opposite sides of one operand), and `end_of_options`. It also states the two traps the corpus itself produced: `readonly` is not "safe" once `open_world` is set, and a command can destroy without any destructive-looking flag.

- **`LICENSE` was missing.** `Cargo.toml` declared `license = "Apache-2.0"` and the README carried the badge, but the repository shipped no licence text at all — so the one artifact that makes the declaration actionable was absent from every clone, tarball and `cargo package`. Added.

- **`overlay_dirs`: overlay directories beyond `~/.apexe/overlays/`.** The user overlay directory was hard-coded as `<config_dir>/overlays` and `config.rs` did not mention overlays at all, so the only ways to add a curated overlay were to copy files into the operator's own directory or to name one file per invocation with `--overlay`. Neither works for a corpus somebody else maintains — a team policy repository, a checked-out data set, a plugin that ships overlays — because both mix third-party content into a directory apexe also treats as the operator's scratch space, and neither survives the corpus being updated. `overlay_dirs` in `config.yaml` (or `APEXE_OVERLAY_DIRS`, `:`-separated like `PATH`) names extra directories to read. Additive by construction, like `additional_denied_paths`: the personal directory is always read and no setting removes it.

  **Order is load order, and later wins**, which is the part that needed deciding rather than just implementing. Configured directories are read first, in the order listed, and `<config_dir>/overlays` is read last, so a hand-written local file shadows a distributed corpus describing the same `(command, variant)` — the same rule that already governs built-in versus user overlays: the source closer to the operator ranks higher. `--overlay` still wins outright. That tie-break was previously an *implicit* property of `OverlayStore::select` using `max_by_key`, which keeps the last of several equally-ranked entries; nothing said so and nothing tested it, so a refactor to `min_by_key`, a sort, or a `HashMap` would have silently inverted the precedence while every other test stayed green. `test_last_loaded_dir_wins_among_equally_ranked_overlays` now pins it.

  A configured directory that does not exist is a **warning**, not silence: `load_dir` already treats a missing directory as `Ok(0)`, which is right for the personal directory (most installs never create one) and wrong for a path an operator typed, where it is indistinguishable from an empty directory. Each loaded directory logs its file count so an operator can confirm a corpus was actually picked up. Verified end to end against a real `apexe scan`: via `config.yaml`, via `APEXE_OVERLAY_DIRS`, with two directories where the later one wins, and with a missing directory that warns and lets the scan continue.

- **`find` and `xargs` now declare `open_world` in all four overlays.** Both spawn whatever program the caller names, so `openWorldHint: false` -- which is what they emitted to every MCP client -- was a false statement about the domain of interaction rather than a missing one. Probed on macOS 26.5.2 and in Debian: `echo hello | xargs /bin/echo SPAWNED:` and `find . -name t.txt -exec /bin/echo SPAWNED: {} \;` both spawn, and substituting `curl --version` for the echo reaches a network client from inside a `find` walk. This is asserted rather than inferred on purpose: `infer_open_world` reads two name lists that both mean *network*, and exec wrappers are deliberately routed through `destructive` instead (see the comment on `EXEC_WRAPPER_TOOLS`), which is the classification that actually drives the ACL and the path guard. That routing is left intact -- the overlays add `open_world` on top of `destructive` rather than moving between them.

  **This changes no access decision.** Both are already `destructive`, so they are already in the destructive deny rule, and `open_world_ids` excludes destructive modules so an id is never listed in two deny rules; `risk_from_annotations` likewise ranks destructive above open-world. Verified on a real `apexe scan find xargs curl`: `cli.find` and `cli.xargs` stay in the destructive rule alone while `cli.curl` occupies the open-world rule. The only observable change is `openWorldHint` flipping false to true in `tools/list`, confirmed against a live stdio MCP server before and after.

- **The generated ACL gained an open-world tier, and the auto-allow rule no longer covers a command that reaches the network.** `apexe scan` classified modules into two buckets — `readonly` → `allow`, `destructive` → `deny` — and everything else, including every networked command, was denied by `default_effect: deny` while matching no rule at all. On a stock policy that is the right outcome reached the wrong way. It stops being right the moment an operator sets `default_effect: allow`, where silence becomes blanket network access; and it leaves an operator who wants `git fetch` back with no rule to edit, only the option of discovering by trial which module ids were denied by the absence of a rule. `open_world_ids` now builds a third unconditional `deny` rule ("Block open-world CLI commands by default"), carried through `merge_default` like the other two. On a real `apexe scan git curl` this moves `cli.git.clone`, `cli.git.fetch`, `cli.git.pull`, `cli.git.push` and `cli.curl` out of "matched no rule" and into a named one; the readonly and destructive rules are unchanged.

  **`readonly_ids` now excludes `open_world` modules.** `readonly` is a claim about local state — the command does not modify the machine — and says nothing about what it *sends*; a read that reaches the network is the exfiltration shape, not the safe shape. Rule evaluation is first-match-wins and the readonly `allow` is written before the open-world `deny`, so a module in both lists would have been allowed by whichever rule came first — a correctness question settled by list order, which is what breaks silently when a rule moves. The three lists are kept disjoint instead (a destructive open-world module is listed once, under destructive), so no ordering makes the policy wrong, including in a file whose rules an operator has since rearranged. Inference alone never produces `readonly` + `open_world` — the two name lists do not intersect — so this closes a latent case rather than a live one, and the case became reachable when `open_world` joined the overlay schema in this same release.

  Deliberately **not** `allow` + `approval: required`, which is the other defensible reading of "the network needs a human": that loosens the shipped default from deny to allow-with-a-prompt, and being reachable is a decision an operator should make explicitly rather than inherit from a generated file.

  One trap found while testing, worth recording because the next person will hit it: **apcore's `ModuleAnnotations::default()` sets `open_world: true`** (MCP's conservative `openWorldHint`). The ACL test fixtures built annotations with `..Default::default()`, so adding the `!open_world` filter silently emptied the auto-allow rule in three existing tests. Real modules are unaffected — `annotations::infer` always sets the field explicitly, verified against a live `apexe scan git curl` — but the fixture helper now sets it explicitly too, the same fix `adapter::contract`'s helper already carries for the same reason.

- **An overlay can now assert `open_world`.** The other four behavioral annotations were already overridable from an overlay; this one was not, and it is the one that needed it most. `open_world` is the only annotation inferred from a *name list* rather than from the command's own scanned surface — an executable in `OPEN_WORLD_TOOLS` (`curl`, `ssh`, `rsync`, …) or a networked subcommand in `OPEN_WORLD_SUBCOMMANDS` (`push`, `clone`, `login`, …) — which makes it a floor that cannot see a boundary a name does not advertise, and, worse, cannot express a boundary that *differs between variants of one name*. GNU sed runs the replacement as a shell command for `s///e` (`printf 'x\n' | sed 's/x/echo PWNED/e'` prints `PWNED`; `--sandbox` refuses it with `e/r/w commands disabled in sandbox mode`), while BSD sed rejects the flag outright with `bad flag in substitute command: 'e'`. One name, two answers. `docs/user-manual.md` already told authors that "an overlay's `annotation_overrides` is the way to state the truth for a specific one" — the schema and the `AnnotationOverrides` struct simply did not carry the field, so that instruction could not be followed.

  The previous behaviour was silent rather than diagnosed, which is why this is a fix and not a feature. `tool-overlay.schema.json` set `additionalProperties: false` on `annotations` and listed only the four, so an overlay naming `open_world` was invalid — but nothing enforces that schema at load time (`validate_overlay` is hand-written Rust, not a JSON Schema check), and `AnnotationOverrides` does not set `deny_unknown_fields`, so serde dropped the key without a word. An overlay asserting `open_world: true` therefore loaded, applied its other annotations, and emitted `open_world: false` into the binding with no error and no warning.

  Added to the schema's `annotations` block, to `AnnotationOverrides` as `Option<bool>` (unset still leaves inference alone), and honoured in `apply_annotation_overrides`. Both directions work: an overlay can raise `open_world` on a command no name list catches, and clear it on one a name list catches wrongly. `overlays/sed@gnu.json` now asserts `true` and `overlays/sed@bsd.json` asserts `false` as a checked negative, each with the probe recorded in `provenance.notes`. Note that this only changes what an overlay can *say*; `risk_from_annotations` already read the field, and `destructive` still outranks it when the annotations are reduced to one `Risk`.

- **`overlays/` and `BUILTIN_OVERLAYS` are now checked against each other.** The list of `include_str!` entries in `src/scanner/overlay_store.rs` restates what the `overlays/` directory already knows, and only one direction of that duplication was guarded: a registered id whose file is gone is a hard compile error, while a file nobody registered was silently dead — present in the repo, passing review, reading as shipped, covered by no test, and never reaching a user. `test_every_overlay_file_is_registered_as_a_builtin` closes the unguarded direction and names the offending files in its failure message. `docs/overlays.md` gained the step it was missing: its authoring checklist ran from "confirm scanning cannot do the job" to "run `cargo test`" without ever mentioning that a built-in has to be registered, and a new "Where the file goes" section now separates the two destinations — `~/.apexe/overlays/`, which needs no code change and outranks the built-ins, from `overlays/`, which is compiled in and needs the entry. The list stays hand-written on purpose (see the comment on `BUILTIN_OVERLAYS`): the intent is that adding to it is a decision, not that forgetting it is undetectable.

- **`sed` overlays for the `bsd` and `gnu` variants.** Both `authoritative` + `verified`. BSD was checked against macOS 26.5.2's `/usr/bin/sed`, with the option set closed by the getopt(3) string `EHI:ae:f:i:lnru` read out of the binary; GNU against Debian's sed 4.9 and re-checked against Homebrew's 4.10, with the long-option table *enumerated* rather than transcribed — `getopt_long` resolves an unambiguous prefix and names the candidates for an ambiguous one, so sweeping `--<letter>` over a-z closes the set at 18 options and catches two that `--help` does not list at all (`--binary`, `--zero-terminated`). The traps each variant carries are recorded in `provenance.notes`, chiefly that BSD's `-i` requires its extension operand while GNU's forbids separating it — `-i.bak` is the only spelling that works on both — and that the `w` function truncates its target before any input is read, on both variants, with no `-i` anywhere on the command line.

## [0.7.0] - 2026-09-02

### Added

- **`apexe serve`/`apexe a2a` no longer register a module whose binary is gone.** A binding file is a snapshot taken at `apexe scan` time; nothing re-checked it afterward, so a tool uninstalled, moved, or scanned on one host and served from another stayed listed in `tools/list` and reachable by `module_id` — it just failed every call with `ModuleNotFound`/"not installed", which is a worse outcome for an MCP/A2A client than not being offered the tool at all. `filter_available` (`src/module/registry.rs`) now runs inside the shared `build_executor`, right after `ModuleFilter`, and drops any module whose `target` (`exec://{binary_path} ...`) does not resolve on this machine — an absolute path is checked on disk, a bare name against `PATH` (`scanner::resolver::target_is_available`, a plain filesystem/PATH lookup, not the `--version` probe `ToolResolver::resolve` does, since this runs once per module and has to stay cheap). Because both server builders share `build_executor`, this applies to MCP and A2A alike, and — unlike `--tags`/`--prefix` — it is unconditional: there is no flag to turn it off, since an external caller has no reasonable way to recover from being told a tool exists when it does not. Each exclusion is logged (`WARN … module_id=... target=...`) so a sudden drop in the tool count is traceable. `apexe list` gained the same check as `--available-only`, opt-in rather than default there, since the plain listing is also used to review everything ever scanned (e.g. before copying `modules_dir` to a new host). Documented in `docs/user-manual.md` §10 "Availability Filtering".

- **A path guard refuses a wrapped tool pointed at a system directory.** The ACL decides *whether a module may be called* and cannot decide *what a call may touch*: apcore ACL rules match on `callers` and `targets` — module ids — and every registered condition key (`identity_types`, `roles`, `max_call_depth`, `$or`, `$not`) is a fact about the principal, never about an argument. So the only policies expressible for `rm` were "allowed" and "denied", and the one that matters is neither: `rm` is not a command to forbid outright, `rm /etc` is. Nothing else covered the gap either — `validate_argument_value` checks for control characters and a leading `-`, and `/etc/passwd` has neither, so `{"file": ["/etc/passwd"]}` reached `execve` verbatim. `src/governance/path_guard.rs` now resolves and checks every argument the input schema types as a filesystem path (`x-apexe-path`, which the schema builder already emitted for `ValueType::Path` — `apexe scan rm` produces it on `file`'s `items` today, so no binding has to be regenerated). There are **two compiled-in baselines**, because reading and writing are different risks and one list forced a single answer onto both. *System paths* (`/etc`, `/usr`, `/var`, the macOS system directories) bind a module that can write; a module annotated `readonly` may name them, because refusing `cat /etc/hosts` and `ls /usr/bin` protected nothing — those files are world-readable and an agent's own file tools reach them regardless — while costing every legitimate diagnostic. *Credential paths* (`~/.ssh`, `~/.aws`, `~/.gnupg`, `~/.kube`, `~/.docker`, `~/.apexe`) bind **both** modes, because the asymmetry runs the other way there: a deleted private key announces itself the next time the key is used, while one copied into a model context leaves no trace at all, so the stricter treatment goes to the risk that is harder to notice. `~/.apexe` is on that list rather than the system one because it holds the ACL and audit trail governing the very call being made. `~/.config` is deliberately on neither — it holds ordinary application settings a wrapped tool has legitimate reason to touch. Neither list can be shortened, and `config.yaml`'s new `additional_denied_paths` appends to the *credential* one, so a configured path binds readers too: an operator naming a path explicitly is asserting it is sensitive, and the stronger reading is the one that cannot be wrong in the dangerous direction. Confining the boundary to code is the point: this deliberately did **not** go into the overlays, where it would have had to be restated per command, would have left every tool no overlay covers unguarded, and would have expressed a security boundary in a data file that `mode: authoritative` lets any other data file replace.

  **What is compared is the path the kernel would act on, not the string the caller sent.** Three transformations sit between them and skipping any one makes the guard decorative. Relative paths are joined to the guard's root — which is now also what `Command::current_dir` is set to, closing a second defect found on the way: the child previously *inherited* apexe's working directory, so the meaning of every relative argument depended on which directory the operator happened to launch `apexe serve` from, and the guard and the child had no guarantee of agreeing on it. Symlinks are followed, because `/tmp/x -> /etc` makes `rm -rf /tmp/x/` a request to delete `/etc` that no string comparison sees; the longest *existing* prefix is canonicalized, so a destination that does not exist yet is still judged. `..` is folded last and only across the non-existent tail — `std::path::absolute` preserves it because POSIX requires it, and collapsing it lexically first is wrong, since `/tmp/link/..` is the parent of link's target rather than `/tmp`. The check then runs in two directions, of which only one binds a reader. *Containment* — the path sits inside a protected location — applies to both modes and is what refuses `cat ~/.ssh/id_rsa`. *Ancestry* — the path sits above one — applies to writers only, because it exists for the recursive operation that takes the protected directory with it: `rm -rf /` never names `/etc` and destroys it regardless. Holding a reader to it would refuse `ls ~` and `ls /` on the grounds that a home directory contains `.ssh`, which is most of what a reader does; the cost is that a recursive *read* rooted above a credential directory (`grep -r … /`) is not caught, and that is stated in the threat model rather than papered over. Matching is per path component either way, so `/etcetera` does not collide with `/etc`.

  Two findings from writing the tests, both of which changed the design. `/` cannot be a baseline entry — every absolute path starts with it, so the containment test matched unconditionally and the first build refused the entire filesystem; `rm /` is instead caught by the ancestor direction, which is the only one that carries the intended meaning. And on macOS the per-user temp directory *is* `/var/folders/<x>/<y>/T`, so guarding `/var` refused every use of the directory whose entire purpose is being written to; a compiled-in carve-out keeps it usable, `config.yaml` cannot extend that list, a `TMPDIR` equal to or containing a *system* entry is discarded rather than honoured, and where a denied entry and the carve-out both cover a path the more specific one decides — with a tie going to the refusal. Weighing the credential list in that discard check was a third finding, and a bug: a home directory under `$TMPDIR` — ordinary in a sandbox or CI container — made every credential path a descendant of the carve-out, which voided it, which re-armed `/var` across the whole temp directory. Specificity already protects a credential path nested inside the carve-out, so the check consults the system list alone. A refusal is `ACL_DENIED` rather than `GENERAL_INVALID_INPUT`, which is both accurate (this is a governance decision, not a malformed value) and load-bearing: `breaker.rs` excludes governance refusals from circuit-breaker health, so a caller repeatedly probing `/etc` cannot open a circuit and deny `cli.rm` to every other caller. It carries the requested path, the resolved path and the protected location that matched — the requested one frequently does not look protected, which is the whole point of resolving it. Unlike `--acl` and `--enable-approval`, the guard is **on by default on every surface and has no off switch**; the access mode is the one thing that varies per call, and a module with no `readonly` annotation is treated as a writer. Documented in `docs/threat-model.md` §4.8 and §5.8 and `docs/user-manual.md` §9.7; the limits are stated there rather than implied, chiefly that a value the schema does not type as a path is not seen, that a recursive read above a credential directory is not caught, that the mode is per module rather than per argument (so `cp /etc/hosts ~/backup` is refused even though the system path is only being read), and that nothing bounds what the tool does after it starts.

- **`config.yaml` gains `allowed_paths`, the one setting that relaxes the path guard.** Empty by default, so the feature is inert until an operator writes it down. It exists because the rigid version was worse in practice: an agent that legitimately has to write `/etc/nginx/conf.d` had no option but to be handed that tooling *outside* apexe, which drops the audit trail and the ACL along with the path check — `docs/threat-model.md` §5.1 in miniature, reached by way of a control too inflexible to use. Nothing validates that a carve-out is wise: naming `/etc`, or a credential directory, is honoured, because overruling an explicit instruction would put the guard in the business of second-guessing whoever deployed it, and an operator staring at a config file that appears to do nothing is its own failure mode. What the guard does instead is refuse to be quiet — every carve-out is logged at startup, and one that opens a whole system location or exposes credentials is logged at `warn`. Carve-outs and denials share one specificity ladder, so a subtree can be opened and part of it fenced off again with `additional_denied_paths`. An exact tie is broken by *provenance*: a configured `allowed_paths` entry wins because it is an instruction, while the derived temp-directory exemption loses because nobody asked for it and an exact overlap there is a coincidence — which is what keeps a `TMPDIR` pointed at `~/.ssh` from reading a key out. Two properties are documented rather than implied: a carve-out grants everything beneath it, and one over a service's configuration directory grants that service's behaviour (`/etc/nginx/conf.d` write access is enough to add a `proxy_pass`).

- **`examples/path_guard`** — a runnable companion to `examples/acl_demo`, kept separate because the two answer different questions: an ACL decides who may call which module, the guard decides what one call may touch. It registers a reader and a writer with an identical path-typed schema, differing only in the `readonly` annotation, and prints the four quadrants plus an `allowed_paths` carve-out against the same paths. `cargo test --example path_guard` asserts the contract. `acl_demo`'s README now points at it, since that demo's role rules are the boundary that is *not* yet reachable over `apexe serve`, while the guard always is.

- **`apexe policy` reports the filesystem boundary without starting a server.** The path guard added above is always-on and has no off switch, which makes "what can this module actually reach" a question an operator has to be able to answer — and until now answering it meant standing up `apexe serve` and driving it with an MCP client. With no arguments the command prints the guard **as installed**: the working directory relative paths resolve against, both compiled-in baselines, whatever `additional_denied_paths` added, the `allowed_paths` carve-outs, and the derived temp-directory exemption. That summary is read off the live guard rather than re-derived from `config.yaml`, so it cannot describe a policy other than the one in force — which matters precisely because a misspelled config key leaves the baseline running and nothing else in the process would say so. `--path <p> --mode read|write` goes one step further and calls the guard's own `check`, the exact call a wrapped tool's argument goes through, so a verdict here cannot drift from what a real invocation would get; `--mode` exists because the two baselines disagree on purpose, and `apexe policy --path /etc/passwd` denying while `--mode read` allows is the split working. `--format json` for both. Documented in `docs/user-manual.md` §4.6 and `docs/threat-model.md` §4.8.

- **A curated overlay can state what a flag *does*, for the two things no scan can infer.** Help text does not distinguish `git --exec-path=<path>`, which sets a search path, from `git --upload-pack=<cmd>`, which runs one — both read as "takes a value" to every parser apexe has, and guessing would produce exactly the plausible-but-wrong assertion the overlay rules exist to prevent. `ScannedFlag.risk` (`FlagRisk`) defaults to absent and only a human raises it. **`escalates`** puts the call to the approval gate, and reaches the flags no name list generalizes — nothing about the string `--privileged` suggests danger; it emits `x-apexe-escalates: true`. **`benign`** goes the other way, because the name list matches on spelling and spelling is sometimes a coincidence: `bsdtar -y` is bzip2, `sort -f` folds case, `cut -f` selects fields, and before this the only way to stop the prompt was to assert `requires_approval: false` for the whole command, which also said `tar` may overwrite files unattended. It emits an explicit `x-apexe-escalates: false`, so the keyword is three-state — absent means the name list decides. **`executes`** is not a severity notch above `escalates` but a different claim: apexe's central guarantee is that argv reaches `execve` with no shell on the path, and a flag whose value *becomes* a command hands that guarantee straight back, with no JSON Schema constraining what the string turns into. Such a parameter is therefore **refused outright** by `executor::reject_exec_parameters` (`ACL_DENIED`, effective values only, so `{"upload_pack": false}` is not sending one) rather than gated — an approval prompt would ask a human to predict what an arbitrary string will do, which is the judgement least likely to survive a stream of prompts. It emits `x-apexe-exec`. Known members of that class, none of which look dangerous in a help listing, are listed in `docs/overlays.md`: `git --upload-pack`/`--receive-pack`, `tar --use-compress-program`, `rsync -e`/`--rsync-path`, `find -exec`/`-ok`. This is a floor and a small one — a flag of this class in an un-overlaid tool is not caught, and each assertion must be verified against a real installation before it ships. Documented in `docs/user-manual.md` §8 and `docs/threat-model.md` §4.9.

- **`docs/features/v2-f8-local-execution.md`** — a design for giving the local terminal the same governed path MCP and A2A callers already get. `Executor::call` is reachable only over a transport today, so a shell script, a CI step or a human wanting to see what the ACL would decide has no way in. Two stages, and only the first is ready to build: `apexe run <module_id> --input <JSON>` with a preflight that reports every governance decision (ACL verdict, path-guard verdict per path argument, whether approval would fire) and stops before spawning. Stage 2 — PATH shims, so a wrapped tool is invoked by its own name and its own argv — is blocked on two contracts the spec insists on settling first: an `ExecutionIo` mode for passthrough I/O, and a `streaming_stdin_safe` per-module allowlist, since an inherited stdin is not schema-validated, not path-checked and not recorded. The spec is unusually explicit about what the mechanism cannot do (shell builtins are never intercepted and the gap is invisible at the point of use; an absolute path bypasses any shim), and those four limitations are reserved as `docs/threat-model.md` §5.10 so they land with the feature rather than after it. Design only — nothing here is implemented.

### Changed

- **BREAKING: the approval gate weighs the arguments a call actually sent, and flag boosting no longer happens at scan time.** A scan sees the flags a command *accepts*; a call carries the flags a caller *sent*, and only the second is a reason to interrupt a human. Deriving `requires_approval` from the first marked `git log` — which merely accepts `--all` — as needing human approval on **every** invocation, while `git push --upload-pack=<cmd>` earned exactly the same verdict. Of the 42 shipped overlays 32 declare a flag on `APPROVAL_FLAGS`, and the readers among them (`ls`, `grep`, `diff`, `du`, `df`, `tail`, `cut`) stayed quiet only because a human had written `requires_approval: false` by hand; nothing kept an un-overlaid tool quiet at all. Approval fatigue is not a cosmetic failure — the documented response to a gate that prompts on every read is to switch the gate off, which lands on the ungoverned default. The list is now applied in two halves. `mark_escalating_params` (`src/adapter/converter.rs`) records the *schema property names* carrying those literals in `x-apexe-escalating-params`, with `x-apexe-approval-basis: "flags"` saying the mark came from accepted flags alone, and keeps `requires_approval` true as a **ceiling** — apcore decides whether to run the gate at all from that static flag, and neither `ApprovalHandler` nor its `ExecutionPolicy` hook is handed a call's arguments. `ApprovalGate` then reads the recorded list against the arguments actually sent and stands down when none carry an effective value, recording `approved_by: "apexe-approval-gate"` so an audit reader can tell it from a human's yes. `git log` stops prompting; `git log --all` prompts; `git push --force` prompts. A module marked `destructive` **by name** records no such basis and always prompts — no absent flag makes `rm` safe. Every branch that cannot read the basis prompts, so a corrupted annotation fails toward the human rather than silently bypassing the gate. Names are read off the built schema rather than `ScannedCommand::flags`, because a positional argument can displace a same-named flag onto another key and the schema is the only place the name a caller will send is settled.

  **The `--dry-run` → `idempotent` boost is removed outright**, with no per-call replacement. A command that *accepts* `--dry-run` does not run dry, so the boost made `cacheable` true for a mutating command whenever the caller left the flag off — and the next reader was served a cached result for a call that had changed something. Unlike approval there is no invocation-time hook to move it to, since nothing consults `idempotent` when a call is made; an overlay's `annotation_overrides` remains the way to assert it. Documented in `docs/user-manual.md` §8 and §9.6.

- **Command executors are classified `destructive`, not `readonly`.** `EXEC_WRAPPER_TOOLS` in `src/adapter/annotations.rs` covers `env`, `xargs`, `nice`, `ionice`, `nohup`, `timeout`, `chroot`, `setsid`, `stdbuf`, `script`, `watch`, `time`, `sudo`, `doas` and `su`, and outranks both name-pattern lists. This was live rather than theoretical: `env`'s name is in `READONLY_PATTERNS`, so `apexe scan env` produced `readonly: true`, which earned it an explicit **allow** in the generated ACL and made the path guard judge its arguments as a reader's — and BSD `env` accepts `-S <string>`, which splits that string into argv and executes it. `cli.env` with `{"S": "rm -rf /etc"}` passed both controls; a canary file in a scratch directory was verifiably deleted, and the same call naming `/etc` returned `ALLOWED` rather than `ACLDenied`, confirming the guard never inspected it (correctly, by its own contract — `-S` is typed `string`, and nothing in it is a path). Both `xargs` overlays carried `destructive: false` and were corrected in the same change, since a curated overlay replaces the scan result and would otherwise have overridden the classification silently; a data guard now pins that for every command executor with an overlay. **This is a floor, not a fix**: no static analysis can decide what argv a caller-supplied string will become, so `docs/threat-model.md` §5.9 recommends denying these in the ACL or, better, not scanning them into the registry at all — a wrapped `env` buys nothing that wrapping the underlying tool does not, and costs every control in §4.

- **`PathGuard::new` and `PathGuard::from_env` take a `GuardConfig` instead of a slice.** A struct rather than two slice parameters because `denied` and `allowed` share a type and mean opposite things, and a transposed call would turn a deny list into an allow list with no compiler error.

- **`executor::build_arguments` and `executor::build_argv` take an `AccessMode`.** Both are `pub`, so this is a breaking change for anything outside the crate that renders argv directly. The parameter is what the path guard consults, and it could not be a process-wide value the way the guard itself is: it varies per call. `AccessMode::from_readonly(module.annotations.readonly)` reproduces what `CliModule` passes, and `AccessMode::Write` is the conservative choice for a caller with no annotation to hand.

### Fixed

- **An ACL denial over A2A says it was a denial.** ([#41](https://github.com/aiperceivable/apexe/issues/41)) A refused call reached the caller as `TASK_STATE_FAILED` carrying `Task not found`, and an approval denial as `Internal server error`. Both are worse than vague, they are *actionable in the wrong direction*: `Task not found` names the task id — the one thing that was fine — so an agent retries, or resends under a fresh message id, and is refused identically for as long as it keeps going, while `Internal server error` says the server broke and earns a backoff-and-retry. The correct response to either is to stop and pick a different skill. The mapping is apcore-a2a's (`ErrorMapper::to_jsonrpc_error` decides what a caller is told from the error code alone, and `carries_caller_detail` gates the same text into `status.message`), and **0.6.1 documented it rather than overriding it**, on the grounds that diverging from a convention shared with apcore-a2a's Python and TypeScript siblings to make one host's message nicer was the wrong trade. That reasoning does not survive being stated precisely. The masking exists so an unauthorized caller cannot enumerate what exists — the 404-instead-of-403 argument — and on this server it protects nothing: apcore-a2a already ACL-filters the agent card per caller, so a denied skill is absent from it and the refusal confirms nothing the card had not already settled, and `apexe a2a` wires no authenticator, so every caller is the same anonymous `@external` principal and there is no privileged caller to keep the secret from — apcore-a2a does ship `Authenticator` / `JWTAuthenticator` / `async_serve_with_auth`, apexe just calls the no-auth `async_serve`, so that is a property of this subcommand rather than of the crate. What it costs is the one thing the transport exists to carry. apexe now relays the reason: `DenialReasonRelay`, an apcore pipeline step middleware installed on the A2A executor only, re-codes `ACL_DENIED` / `APPROVAL_DENIED` / `APPROVAL_TIMEOUT` to `GENERAL_INVALID_INPUT` — the one code upstream forwards a message for that does not additionally assert something false about *where* the problem is — keeping the original code at the front of the message so the two transports read alike, and attaching guidance that closes the retry loop explicitly. A caller now receives `Invalid input: [ACLDenied] Access denied: caller 'None' cannot access module 'cli.ls' (An access-control rule refuses this call. The task id is fine — retrying it, …)`. The `Invalid input:` prefix is upstream's. Nothing else changes: the ACL still decides, `audit.jsonl` still records the decision with the matched rule index and the caller's `trace_id`, MCP is untouched (it already reported `[ACLDenied] …` from the code itself, so relaying there would swap an accurate code for a re-coded one), and an approval *pending* is deliberately left alone — apcore-a2a maps it to `TASK_STATE_INPUT_REQUIRED` carrying the `approval_id` a caller resumes with, which re-coding would turn from a resumable pause into a terminal failure.

  Two of the issue's incidental notes, resolved: `Task not found` is **not** the fallback arm of a short match — it is an explicit arm, and `MODULE_NOT_FOUND` was already mapped correctly (`-32601` with its own message intact), so an unknown skill still reads as missing and the fix does not blur the two. `APPROVAL_DENIED` and `APPROVAL_TIMEOUT` *were* mis-served, landing in the catch-all `Internal server error`, and are relayed with the same mechanism.

- **The agent card's `url` and `protocolVersion` are pinned, and were never missing.** ([#41](https://github.com/aiperceivable/apexe/issues/41), third incidental note) The card was read as omitting `protocolVersion`, `url` and `preferredTransport` because only `supportedInterfaces` was present. That *is* where they live: A2A 1.0 replaced the three 0.3 top-level fields with one entry per transport endpoint carrying `url`, `protocolBinding` and `protocolVersion`, and apexe's card has all three (`http://127.0.0.1:8793`, `JSONRPC`, `1.0`). No change beyond a test that pins it, so a reader expecting the 0.3 shape can see where the fields went and a regression in the `url` apexe stamps fails here. The other two incidental notes are apcore-a2a's dispatcher and its stream-event encoding, neither of which apexe sits in front of: a JSON-RPC notification getting a reply, and SSE frames using the protobuf `oneof` key (`statusUpdate` / `artifactUpdate`) instead of a `kind` discriminator.

- **Tests: what a refused caller is told is now asserted over the real request path.** The previous coverage anchored the manual's claim to `ErrorMapper::to_jsonrpc_error`, which is upstream's decision function and not the bytes a client receives. `tests/a2a_integration.rs` now drives a `message/send` through the apcore-a2a axum router built from the exact governed `Executor` `serve` assembles (`A2aServerBuilder::executor`, new, the in-process counterpart of `agent_card`), and reads `status.message` off the response — so a regression fails on the delivered text rather than on a remembered mapping. The upstream premise is still pinned separately: if apcore-a2a starts reporting the reason itself, the consistency test fails and says to drop the relay rather than restore anything.

## [0.6.1] - 2026-08-24

### Fixed

- **An optional-value long option in a curated overlay carries its value again.** ([#40](https://github.com/aiperceivable/apexe/issues/40)) The [#24](https://github.com/aiperceivable/apexe/issues/24) fix gated the `--flag=value` spelling on `x-apexe-value-optional`, which help-text scanning recovers from `--opt[=VAL]`. That marker has been declarable in an overlay since 0.6.0 — the loader, `schemas/tool-overlay.schema.json` and the emitted contract all honour it — and **no overlay set it**, on any flag, in any of the 42 shipped files. So every optional-value long option in the curated surface rendered `--flag value`, which these tools read as *"no value, and here is an operand"*. It is a wrong answer rather than a refusal, and it fails in two directions at once: `cli.ls {"color": "never", "file": ["."]}` submitted `never` as a file that does not exist **and** left colour on, because a bare `--color` means "always"; `cli.grep {"color": "never", "pattern": "hello", ...}` pushed `never` into the pattern position so the pattern became a filename. `mkdir --context ctx d` is the worst of the set — exit 0, having silently created a spurious directory. 34 flags across 17 overlays are now marked. Each was established by running **both** spellings against the build its overlay's provenance records: the GNU half in the pinned `debian@sha256:328d1649…` reference image (coreutils 9.7, diffutils 3.10, grep 3.11, findutils 4.10.0), the BSD half against macOS's system binaries. The scope was re-derived rather than transcribed, and the shape it produced differs from the filed inventory in both directions — 20 of its 31 entries hold — 11 listed flags take a *required* value (`ls --sort`, `--format`, `--time-style`, `--quoting-style`, `--indicator-style`, `grep@gnu --context`, `du --time-style`, `sort --sort` on both variants) or no value at all (`ls --context`, `mv --context`, which are `-Z`), and 14 unlisted ones are optional (`cp --update`, `diff --unified` on both variants, `mv --update`, `df --output`, `rm --interactive`, `--preserve-root`, `sort@apple --check` — the flag the filed entry for that overlay should have named — `tail --follow`, `uniq --all-repeated` on both variants, `uniq --group`, `xargs --eof`, `--replace`). Two facts are why this has to be a per-flag assertion and not a heuristic: **an enum is not evidence** — `--color` is enum-valued and optional while `--sort` is enum-valued and required — and **a variant is not evidence**, since BSD `grep --context` takes an optional value while GNU `grep --context=NUM` requires one, the same flag name with the opposite argv shape.
- **An optional-value flag's contract no longer forbids the bare form it advertises.** Found while fixing the above and shipped with it, because 23 of the 34 flags reach it. `scalar_flag_schema` emitted `"type": ["string", "boolean"]` with `x-apexe-value-optional` *and* an `enum` listing only the words. `type` and `enum` are independent assertions a value has to satisfy both of, so `true` — the spelling the union exists to permit, and the only way to reach `ls --color` bare — was rejected by the enum, leaving one of the two legal forms unreachable through the contract. Both booleans now join the list: `true` selects the bare flag and `false` omits it, which is what the executor already does with either.
- **A repeatable flag no longer loses its optional-value marker or its allowed values.** The same defect as the first entry, one branch along, found while verifying that fix. `flag_to_schema` dispatches to two builders that were written independently, and the array one never learned about `value_optional` or `enum_values`: a flag that repeats got `items: {type: "string"}` with no allowed-value list and no `x-apexe-value-optional`, so the executor rendered `--flag value` per occurrence and every one of those values became an operand. Both fields are settable together today — `schemas/tool-overlay.schema.json` lists them side by side, and on the scan path `value_optional` comes from `--opt[=VAL]` in `scanner::man_page` while `repeatable` comes from `parsers::gnu`, which infers it from a description containing `"..."` or `"can be repeated"` — so the two are independent inferences over the same merged flag and nothing prevents their meeting. **Nothing hits it today**: across the 42 shipped overlays and 1702 flags from 16 freshly scanned tools, `repeatable + value_optional` co-occurs 0 times and `repeatable + enum_values` 0 times, so no emitted contract changes shape. This is hardening against a recurrence, not a live user-facing bug — but it is the third time this file has dropped a per-flag fact on the array branch alone (`format_hint` was the first, fixed in 0.6.0), so the `enum` list now comes from one shared `enum_constraint` that both builders call. The booleans are added on the scalar branch only, and deliberately: an array's element type is not a union and the executor has no spelling for a bare occurrence inside one — it renders every element as `--flag=<element>`, so admitting `true` there would advertise the literal `--flag=true`. The bare form stays unexpressible for a repeatable flag, which is a stated limit rather than a wrong render.
- **`SCAN_FORMAT_VERSION` is bumped to 3, so an existing install actually receives the fix.** Overlays are compiled in with `include_str!` and, in `authoritative` mode, *are* the answer for the tools they cover — so correcting one changes the emitted contract for a binary whose name, variant and version are all unchanged, which is exactly what the version component of the cache key exists to catch. Without the bump `apexe scan ls` returns the pre-fix contract from cache at exit 0 with nothing saying so, and `--no-cache` is the only escape: the failure mode the key was introduced for, reached through overlay data instead of scanner code. The field's documentation now says overlays count.
- **Tests: the shipped overlay data is pinned to the spellings the executor renders.** `build_arguments` already had unit tests for both classes; nothing tied them to the curated files, which is how the whole overlay surface came to render the wrong form with the suite green. Two data guards assert the 34 flags are marked and — the half that stops the tempting `enum_values` shortcut — that the near-misses above stay unmarked, both without needing the matching host. Two end-to-end tests run the real `ls` in both spellings on either userland: `--color=always` colourises and `--color=never` does not, proving the value lands, while the unmarked schema's `--color never` fails on the phantom operand and colourises anyway, proving the marker is what makes the difference.

## [0.6.0] - 2026-08-21

### Changed

- **Upgraded to apcore 0.27, apcore-mcp 0.18 and apcore-a2a 0.5, which closes two defects apexe had been working around.** `apcore-cli` moved to 0.10.5 in the same change and had to: 0.10.4 still required apcore 0.26, so the graph carried two incompatible `apcore` versions and apcore-mcp failed to build with `expected apcore::module::ModuleAnnotations, found ModuleAnnotations`. No apexe source change was needed — none of apcore 0.27's breaking changes reach this crate, including `Registry::describe`, whose signature *and* return shape changed without appearing in the upstream changelog at all.
- **`--transport sse` is served again, and no longer needs an acknowledgement.** ([#27](https://github.com/aiperceivable/apexe/issues/27)) apexe refused it because apcore-mcp shared one process-global channel across every connection: responses went round-robin to whichever stream was next, so with two clients connected **one client received the other's tool output**. apcore-mcp 0.18 scopes a session per connection and emits the `event: endpoint` a spec-compliant client waits for, so the confidentiality defect that justified refusing is gone and the refusal went with it. The `apcore-mcp = "0.18"` requirement is what makes that safe to assume — resolving back to the affected 0.17 would take a manifest edit, not a lockfile drift. SSE remains *deprecated upstream*, so apexe warns at startup and `--transport http` stays the recommendation.
- **The audit trail records refused calls, and names who made them.** ([#31](https://github.com/aiperceivable/apexe/issues/31), [#36](https://github.com/aiperceivable/apexe/issues/36)) `audit.jsonl` held only the calls that *ran*, so a caller probing the argv guards or hitting the approval gate left no trace in the one file an audit exists for — the sequence most worth capturing was the one it could not show. apexe now owns the record instead of delegating to `apcore_cli::AuditLogger`, and writes an `event: "refusal"` row from two places, because no single one sees every refusal: `FailureLogMiddleware` covers `input_validation` and everything after it, and `ApprovalGate` covers the approval gate, which apcore runs *before* the middleware phase where a middleware could observe it. ACL denials are deliberately left to apcore's own richer entry rather than double-counted with less detail. Refusal rows are written regardless of `--no-logging`: that flag governs the `tracing` stream, and turning the operational log down must not turn the audit trail off. **Breaking for audit-log consumers**: `event`, `trace_id` and `caller_id` are new; `user` and `input_hash` are gone. `user` came from `getlogin()`, which returns the owner of the controlling terminal — under a service manager that is `root` or the terminal's owner, never the caller, so it attributed every request to the wrong principal, and `caller_id` (the authenticated identity, `@external` for an unauthenticated inbound request) replaces it with something true. `input_hash` was salted with 16 random bytes that were then discarded, so no input could ever be checked against it; a field nothing can verify is not a privacy control. See §9.2 for all three record shapes the file now contains.

### Fixed
- **`apexe scan --dry-run` and `--verify`, and a global `--timeout`.** ([#37](https://github.com/aiperceivable/apexe/issues/37)) `docs/features/v2-f7-config-integration.md` §8 listed all three as shipped capability and none existed — the flags were absent from `ScanArgs` and `Cli`, so the doc described a surface a reader could not use. `--dry-run` reports what would be written for all three deliverables (bindings, ACL, skills) and touches nothing; `--timeout` overrides `default_timeout` from `config.yaml` the way `--log-level` overrides `log_level`, and refuses 0, which would kill every call before it started.

  `--verify` deviates from the F7 wording deliberately. The spec said "run YAMLVerifier + SyntaxVerifier", but `SyntaxVerifier` parses its input as **Rust source** (`syn::parse_file`) — it is for code generators, and pointed at a YAML binding it fails every time. The real gap was elsewhere: `YAMLVerifier` already ran on every write and `write_bindings` discarded its verdict, so a binding that does not parse was reported as `Generated binding` and the command exited 0. A verification failure is now always a warning, and `--verify` escalates it to a non-zero exit — the form a pipeline needs, while a scan whose other tools succeeded still keeps its deliverables by default.

- **`ApexeConfig::ensure_dirs` returns the crate's domain error.** ([#37](https://github.com/aiperceivable/apexe/issues/37)) It returned `std::io::Result<()>` against an F7 spec that documented `Result<(), ModuleError>`, so the one failure every run passes through rendered as a bare io error rather than through `report_error` with a code like every other apexe failure. The message now names the directory that could not be created.

- **`--explorer` on stdio warns instead of silently doing nothing.** ([#37](https://github.com/aiperceivable/apexe/issues/37)) The flag was applied unconditionally, so `apexe serve --transport stdio --explorer` wired explorer routes onto a transport with no HTTP surface: accepted, no UI, no diagnostic. It now behaves like `--metrics`, which had the transport gate all along — one warning, and nothing mounted. The decision lives in a named predicate because on stdio the effect is unobservable from outside, so a test cannot reach it any other way.


- **`--enable-approval` prompts a human again, through the connected MCP client.** ([#29](https://github.com/aiperceivable/apexe/issues/29)) 0.6.0 replaced a prompt that could never be delivered with an honest unconditional deny gate. apcore-mcp 0.18 removed the reason for it: the router now registers the connection's `ElicitCallback` per tool call and puts its *id* in `Context.data` under `MCP_ELICIT_CALL_ID_KEY`, which a handler built outside the router — all a CLI entry point can build — exchanges for the live callback. An id is a `serde_json::Value` where a closure is not, and that was the whole obstacle. Verified end to end over stdio: a client declaring `capabilities.elicitation` receives `elicitation/create`, `accept` runs the call and writes the file, `decline` refuses it. **A client that declared no elicitation support still cannot be prompted and is still refused** — the gate is fail-closed, and against such a client `--enable-approval` remains an unconditional deny over every `requires_approval` module. This needs apcore-mcp 0.18; `apcore-mcp = "0.18"` in the manifest is what makes that safe to assume.
- **`DenyApprovalHandler` is replaced by `ApprovalGate`, which wraps apcore-mcp's handler rather than standing in for it.** Breaking for library consumers: the type is renamed and `new()`/`with_audit()` keep their shapes. It exists for two things upstream cannot do from where it sits. **Auditing**: apcore runs `approval_gate` ahead of `middleware_before`, so a refusal there reaches no middleware and nothing else in the stack records it — the audit work above would otherwise have regressed the moment the handler was swapped. **A reason with a remedy**: upstream refuses an unpromptable client with `Elicitation returned no response`, which names the mechanism and no way out of it; that is the same opaque-refusal failure mode #29 was filed about, one layer along. A human's own decline is passed through verbatim — it is already clear. The decision lives in a `classify` function rather than inline, because driving the real handler can only ever produce a rejection, so an approval mistakenly audited as a refusal — `APPROVAL_DENIED` in the trail for a call that actually ran — was undetectable until the `Granted` arm could be reached from a test.
- **The Explorer's Try-It editor no longer prefills a call that is empty but looks valid.** ([#38](https://github.com/aiperceivable/apexe/issues/38)) `defaultFromSchema` filled *every* schema property — `""` for a string, `0` for a number, `false` for a boolean — so opening `cli.curl` produced 259 lines and 5637 characters of blanks in a textarea 120px tall. Because a present-but-empty value satisfies both `required` and the declared type, `Validate` answered `✓ Input is valid.` and `Execute` sent it; the wrapped binary was the first thing to object. The fix is upstream in `mcp-embedded-ui` 0.5, reached through apcore-mcp 0.18.1: the prefill now emits only the `required` keys, using each property's declared `default` when it has one and `null` otherwise. `cli.curl` becomes `{"url": null}` — 3 lines — and `Validate` refuses it with `null is not of type "string"` at `/url`, which is the honest answer. **The validator itself was deliberately not touched**: it is a correct JSON Schema validator, and `{"url": ""}` genuinely *is* schema-valid, so "fixing" `Validate` would have broken it. The defect was always the prefill that produced a schema-valid empty payload. Verified end to end against the real 257-property `cli.curl` contract, including that an untouched prefill is now rejected at `input_validation` rather than reaching the subprocess.
- **A caller denied by the ACL no longer receives the resolved binary path and argv through `__apcore_module_preview`.** ([#39](https://github.com/aiperceivable/apexe/issues/39) item 4) This is the one #39 item the previous release could not close: `handle_preview` reported `acl: passed=false` and then ran the module preflight and preview anyway. apcore 0.27 implements PROTOCOL_SPEC §12.8.5.1 — an ACL denial must not invoke either hook, must not emit their checks, and must leave `predicted_changes` empty — so the fix arrives with the upgrade rather than from apexe. Verified over stdio against a deny rule: the denied envelope now carries `predicted_changes: []`, checks ending at the failed `acl` entry, and no occurrence of the resolved binary.

Verification of the governance and transport surfaces — the parts never
exercised over the wire — found that two of the three things documented as
access control were not access control, that the approval gate could only ever
deny, and that credentials passed as tool arguments were written to the log in
plaintext. All of that is fixed here, and the HTTP transports now require a
credential by default.

### Security

- **The manual says how to actually call an A2A skill.** ([#35](https://github.com/aiperceivable/apexe/issues/35) item 1) §11 documented flags and endpoints and never showed a `message/send`, so the first thing a reader tried was prose in a TextPart — and got `TextPart text is not valid JSON: expected value at line 1 column 1`, which names the mechanism and no way out of it. Every apexe skill takes a JSON object (`build_input_schema` always emits `"type": "object"`), so arguments ride in a **DataPart** with `skillId` in the message metadata; a TextPart works only when its `text` *is* the JSON. §11 now shows the request. The issue's framing — that the card advertises `text/plain` while no skill can accept it — is **half right and worth stating precisely**: apcore-a2a 0.5 computes each skill's `inputModes` from its own schema and correctly emits `["application/json"]` alone, which is the field a client routing a call reads. Only the agent-level `defaultInputModes` still carries `text/plain`; that is apcore-a2a's hardcoded default describing what the framework can accept, `APCoreA2AConfig` exposes no field to narrow it, and per the A2A spec a skill's own modes override it. Both halves are now guarded: one test asserts every skill advertises JSON only, another asserts the converter never produces a string-rooted schema — the premise that makes the first true.
- **The manual states what an ACL denial actually looks like on each transport.** ([#35](https://github.com/aiperceivable/apexe/issues/35)) Over MCP a denied caller gets `[ACLDenied] Access denied: caller 'None' cannot access module 'cli.cp'`. Over A2A it gets JSON-RPC `-32001` with the fixed message `Task not found` — apcore-a2a withholds the reason so an unauthorized caller cannot enumerate what exists, the 404-instead-of-403 argument, shared with its Python and TypeScript siblings and locked by an upstream test. apexe does not override it: diverging from a deliberate three-language convention to make one host's message nicer is the wrong trade. But an agent reading `Task not found` concludes its *task id* was wrong, and an operator watching that concludes the ACL is broken and removes it — the #29 failure mode, where an opaque refusal drives someone back to the ungoverned default. §9.1 now says so and points at `audit.jsonl`, which records the real decision on both transports with the matched rule index and the caller's own `trace_id`. A consistency test anchors the claim to `ErrorMapper::to_jsonrpc_error`, so if upstream starts reporting the reason the caveat fails rather than quietly misleading.
- **`apexe a2a` gained `--prefix` and `--tags`, so the A2A surface can be narrowed at all.** ([#35](https://github.com/aiperceivable/apexe/issues/35)) The filter added above for `apexe serve` reached A2A as `ModuleFilter::default()`, hardcoded — the flags did not exist, so `apexe a2a` advertised and executed every scanned module with no way to serve a subset. That gap is worse on A2A than on MCP: `apexe a2a` has no authenticator, so choosing which wrapped binaries the surface exposes is the only limiting mechanism available short of an `--acl` keyed on an identity A2A never establishes. Both flags reuse the registration-level enforcement `--prefix`/`--tags` already had, so an excluded module is absent from the agent card *and* uncallable by name, rather than merely hidden from it.
- **`--prefix` and `--tags` now gate `tools/call`, not just `tools/list`.** ([#28](https://github.com/aiperceivable/apexe/issues/28)) apcore-mcp builds the advertised tool list through `registry.list(tags, prefix, ..)` but routes an incoming call by handing the received name straight to `registry.get`, so the filter was a listing concern that never reached the execution path. `apexe serve --prefix zzz.` advertised zero CLI tools and executed `cli.cp` on request, writing the file; `--tags git` did the same for `cli.curl` and `cli.ssh`. `resources/list` and `resources/read` ignored it too, so an excluded module's documentation stayed readable. The filter is now applied at **registration**, so an excluded module does not exist on the server at all and every lookup path returns `ModuleNotFound` — the same invariant `module_id` registration already holds, applied to the other place the advertised and callable surfaces could diverge. `--acl` remains the per-caller boundary; `--prefix`/`--tags` select a subset of the surface for everyone.
- **Credentials passed as tool arguments are no longer logged in plaintext.** ([#30](https://github.com/aiperceivable/apexe/issues/30)) The logging middleware is on by default and records `inputs=` and `output=` at INFO. apcore's `redact_sensitive` redacts a property only if its schema carries `x-sensitive: true`, and no apexe binding had ever carried that marker — not in any of the 168 real modules under `~/.apexe/modules` — so the redaction the manual credited it with was inert for every module apexe has ever produced. `curl --user alice:S3cr3tPass`, `--oauth2-bearer`, a `Bearer` token in `--header` and a password in a `--data` body all appeared verbatim. The scanner now emits `x-sensitive` on credential-bearing options, and a new `--no-log-arguments` keeps the operational record (module, caller, duration, error) while dropping the payload — so the choice is no longer between logging credentials and logging nothing. **This is not retroactive: the marker is written into the binding file, so a binding scanned before this release carries none and still logs credentials verbatim.** Upgrading apexe does not rewrite bindings already on disk — `grep -L x-sensitive ~/.apexe/modules/*.yaml` lists the ones still affected, and `apexe scan <tool> --no-cache` fixes each. Verified on a real install: a 166-binding `~/.apexe/modules` scanned before the fix redacted nothing, while the same `curl --user alice:<password>` call against a freshly-scanned binding logged `***REDACTED***`. `audit.jsonl` was and remains free of raw argument values.
- **The HTTP transports require authentication by default.** ([#31](https://github.com/aiperceivable/apexe/issues/31)) apexe wraps arbitrary local binaries; the test set alone includes `cli.ssh` (arbitrary remote execution) and `cli.cp` (arbitrary file write). An unauthenticated non-loopback bind is not an API without auth, it is a remote-execution entry point for every executable on the host, and it was one flag away with no warning. The upstream capability (`HttpAuthConfig`, `run_sse_with_auth`) had shipped and was never touched. The default now depends on the transport, because the three have genuinely different trust boundaries: **stdio** keeps no auth — the boundary is the parent/child process relationship, and a token would break every Claude Desktop / Cursor config for nothing; **HTTP/SSE on loopback** requires a bearer token, generated and printed at startup so a local dev server needs no secret management; **HTTP/SSE anywhere else** requires it too, and `--auth none` there refuses to start without the separate `--allow-unauthenticated-bind` acknowledgement. `--auth <token|jwt|none>` is named after the decision rather than after one mechanism, so adding a second does not orphan the flag, and `--auth none` is a mode rather than a `--disable-*` that gets copied out of a tutorial and lives in startup scripts forever. `/health` is exempt for probes; `/metrics` deliberately is not, since its `module_id` labels and call volumes are reconnaissance about what this host wraps. The Explorer's `Authorization` field is now wired to something real, and `POST /explorer/tools/{tool}/call` — a plain-REST execution path that bypassed the MCP envelope entirely — sits behind the same authenticator as `/mcp`.
- **`--no-log-arguments` now drops the payload on the error path too.** The flag set apcore's `log_inputs`/`log_outputs` but left `log_errors` hardcoded `true`, and apcore's `on_error` hook renders `inputs = ?redacted_inputs` — the same partially-redacted argument object the `START` line carries. So a call rejected by schema validation printed the `--data` body and the URL query string that the flag exists to suppress, which is precisely the residual gap the manual already admits the `x-sensitive` heuristic cannot cover. Reproduced: `tools/call cli.curl {"data": "password=hunter2", "bogus_unknown_field": 1}` under `--no-log-arguments` logged the password verbatim. All three flags now follow `log_arguments`. Turning apcore's error record off alone would have been an observability regression — an ACL denial, an approval denial and a schema rejection never reach `CliModule`, so nothing else in apexe announces them — so a new `FailureLogMiddleware` takes that job over with a field set that cannot carry a payload: `module_id`, `trace_id`, `caller_id`, `error_code`, `duration_ms`, and deliberately not `error_message`, since a validation message quotes the value it rejected. A refused call still produces exactly one `ERROR` record either way.
- **A credential on a non-loopback bind now says it travels in cleartext.** The auth default added above closes a remote-execution entry point by requiring a bearer token or JWT — but apexe terminates no TLS and neither does apcore-mcp, so on `--host 0.0.0.0` that credential is readable by anything on the path, and whoever reads it holds the entry point the credential was added to close. The startup notice made it worse by printing `Connect to http://{host}:{port}` next to the token with no caveat, which is the line an operator copies. `resolve_auth` now warns whenever a bind is non-loopback and a credential is required, for both token and JWT, and the generated-token notice carries the caveat itself rather than relying on the `tracing` warning — the two go to different places and can be filtered differently, which is the same reasoning that put the token on stderr in the first place. Loopback stays silent: that traffic reaches no network interface, and the local dev server is the case the generated token exists to make painless. This is a warning rather than a refusal because apexe behind a TLS-terminating reverse proxy is the correct deployment and is indistinguishable from a naked bind from inside the process — refusing would break the right answer to force the wrong one.
- **The generated bearer token is written to stderr, not through `tracing`.** It was emitted with `tracing::info!`, which broke in two directions. At `--log-level warn` the event was dropped while `resolve_auth` still installed the token, so `POST /mcp` answered 401 and no apexe command could recover the value — `--show-config` omits credentials by construction — leaving a server nothing could ever call. And `tracing` goes wherever the operator pointed it: a file, journald, a log aggregator. Routing the credential that guards a remote-execution surface through it persists the secret and often ships it off-host, which is the concern `--no-log-arguments` exists for one layer down. The value now goes straight to stderr, unconditionally and off the log pipeline; `tracing::info!` still announces *that* token auth is on.

### Fixed

- **`--enable-approval` no longer denies everything with an opaque reason.** ([#29](https://github.com/aiperceivable/apexe/issues/29)) It installed `ElicitationApprovalHandler::new(None)`, whose only reachable branch is the `None` one, so every gated call came back `No elicitation callback available` — on stdio, on `POST /mcp`, and on the Explorer REST path, and whether or not the client declared elicitation support in `initialize`. The documented human-in-the-loop flow does not exist and cannot be built from outside apcore-mcp's router: the `ElicitCallback` lives in a side-channel map of `Box<dyn Any>`, while an `ApprovalHandler` receives only the JSON `Context`, which holds the string `"available"` rather than the callback. Failing closed is right; failing closed *silently* is what makes an operator disable the flag and land on the ungoverned default, which is worse than either alternative. apexe now installs its own `DenyApprovalHandler`, which names the module, says the block is unconditional rather than a declined prompt, and points at `--acl` and the library `ApprovalStore`; a warning at startup says the same before the first call. The docs no longer promise a prompt. (**Superseded in Unreleased**: apcore-mcp 0.18 made the prompt reachable, and the deny gate went with it.) Approval *granularity* — `requires_approval` is derived from whether a tool's help mentions an `APPROVAL_FLAGS` entry, so `cli.git.log` is gated while `cli.ssh` and `cli.curl` are not — is unchanged and recorded as a known limitation.
- **A long option's value is only attached with `=` where that spelling is required.** ([#24](https://github.com/aiperceivable/apexe/issues/24)) 0.6.0 attached every long option's value with `=`, on the premise that options with a *required* value accept both forms. That is the GNU convention, not a universal one: curl implements its own option parser and accepts no long option in `=` form, for required and optional values alike, so `--max-time=1` came back `option --max-time=1: is unknown`. It made **134 of `cli.curl`'s 258 properties (52%) unusable** — every long option that takes a value — in the tool `docs/examples/basic.md` is built around. The marker that distinguishes the two cases already existed as of the same release: `x-apexe-value-optional` is emitted on exactly the options that need `=` and on none of curl's affected options. `=` is now used where that marker is present and a space everywhere else, which is right in both directions — `ls --classify=never` keeps working, and a required-value option gets the form GNU also accepts and curl only accepts.
- **`find`'s `-f` and `expression` accept the values they exist for.** ([#25](https://github.com/aiperceivable/apexe/issues/25)) The option-injection guard added in 0.6.0 refuses any value beginning with `-`, which is correct for the case it was written for and wrong for two of `find`'s own parameters. Every `find` primary begins with `-`, so the `expression` operand was 100% unreachable; and `-f` exists *precisely* to introduce a path that would otherwise parse as an expression — its own overlay description says so — yet every route through it was closed, making a directory named `-weird-dir` inexpressible through apexe at all. Refusing the value is one way to stop it being read as an option; `--` is the other, and it is the one the wrapped tools actually provide. apexe now emits `--` where the tool supports it, which is a stronger guarantee than "the value did not look like an option", and keeps refusal as the fallback where it does not. Two related corrections: the rejection message now names the offending array element instead of implying it was the first, and `path` is no longer unconditionally `required`, matching BSD find's second usage form and `path`'s own description.
- **`SKILL.md` frontmatter survives the characters a scanned `--help` actually contains.** The generated document is built from text apexe does not author, and `yaml_scalar`'s quote predicate covered only `\n` of YAML's five line breaks — `\r`, NEL (U+0085), LS (U+2028) and PS (U+2029) all took the plain-scalar branch, and a raw one survives inside double quotes too, so quoting alone would not have saved it. A description carrying one plus a `---` ends the frontmatter block early and pushes the remainder into the Markdown body an agent reads as instructions; a tab (GNU `--help` separates a flag from its description with one, and no scanner stage strips it) breaks the parse on its own. A skill whose frontmatter fails to parse silently does not load, which is the opposite of what `SkillOutput` exists to do. Line breaks are now flattened to spaces before quoting — the same set `module::executor`'s `CONTROL_CHARS` rejects on the way in, for the same reason — and the quoted form escapes tabs, the line breaks and any other control character. `display.title` goes through the same quoting. The frontmatter test now parses the block with `serde_yaml` instead of asserting substrings that hold just as well on invalid YAML.
- **A man-page example containing backticks is no longer truncated.** The `#26` renderer wrapped each invocation in a single-backtick code span, so the first inner backtick closed it: `shar` and `mandoc` both ship EXAMPLES lines using shell command substitution, and the rendered skill showed the agent a *different command* than the man page gives (`` shar `find . -print` | mail ... `` lost its substitution entirely). The upstream renderer this replaced put the same string inside a `json` fence, where it was escaped, so the regression came in with the fix. The span now follows CommonMark's rule: one more backtick than the longest run inside, with the space padding that lets the content begin or end with one.
- **`SKILL.md` states the constraints the scan works hardest to establish.** ([#26](https://github.com/aiperceivable/apexe/issues/26)) The generated skill is the contract summary an agent actually reads, and it dropped three annotations. `x-apexe-conflicts-with` did not reach it at all — `cli.ls` carries mutual exclusion on 24 of its 47 properties and the skill mentioned none of it, so every caller discovered the constraint by violating it. A `x-apexe-value-optional` property, correctly typed `["string", "boolean"]`, rendered as `any` — which tells an agent nothing and is broader than the truth. And man-page invocations rendered as a `json` block with `"inputs": null`, which is the shape of a call taking no arguments: the opposite of what the example demonstrates. apexe now renders `SKILL.md` itself rather than delegating to a formatter that cannot know about `x-apexe-*`: exclusions appear per property, a union renders as `string | boolean` with a sentence on what each side spells, and examples are command lines with one line saying they are not call templates. Examples carrying real structured inputs still render as JSON, so nothing is lost.
- **A2A agent cards advertise their examples.** Module registration hardcoded `examples: vec![]`, discarding the man-page invocations that `apexe scan` extracts and the binding file preserves, so apcore-a2a's skill mapper had nothing to render. Found while checking whether #26's omissions applied to the other contract surfaces.
- **A subcommand's global options render before the subcommand, where they work.** ([#39](https://github.com/aiperceivable/apexe/issues/39)) `cli.git.cat_file {"C": "/some/repo"}` emitted `git cat-file -C /some/repo`, and git's global options must precede the subcommand — after it they are rejected or, as with `-C`, read as a different option belonging to the subcommand. The old rendering answered `fatal: not a git repository`; the new one dispatches correctly. `cli.git.log` alone carried eleven such inert properties (`--git-dir`, `--paginate`, `--exec-path`, `-C`, `-c`, …). This is the class #20 introduced machinery for, but the subcommand token is not an operand and does not come from `build_arguments` at all — it comes from the target URI — so a third placement (`x-apexe-flag-position: "before-subcommand"`) is reported out of the renderer as its own group and interleaved by the module that holds `command_parts`. Only tool-level flags merged into a *subcommand's* schema are marked; the synthesized root command's globals are ordinary flags and do not move. The #18 fix is what made this reachable: before it `cli.git.log` had no subcommand-specific options at all, so the whole contract was wrong in a more obvious way.
- **Unicode line terminators no longer reach the log.** ([#39](https://github.com/aiperceivable/apexe/issues/39)) `CONTROL_CHARS` covered `\0`, `\n` and `\r` only, so U+2028, U+2029 and U+0085 passed the guard and reached the default-on logging middleware verbatim — 62 physical `\n` lines versus 71 under the Unicode-aware line splitting that JavaScript, Java and many log processors use, which means the caller decides where a log consumer sees a line boundary. That is exactly the framing argument 0.6.0 used to justify rejecting `\n`/`\r`; the three are now rejected on the same grounds. `\t`, VT and ANSI ESC are deliberately still allowed — tracing's Debug escaping neutralises them.
- **`format: "path"` is emitted as `x-apexe-path` instead.** ([#32](https://github.com/aiperceivable/apexe/issues/32)) `path` is not in the JSON Schema format registry, and apcore-js hard-fails any call passing a property whose `format` it does not recognise — the inverse of the specification, under which an unrecognised format is an annotation and must not be an assertion failure. 73 properties carried it at the property level and 4 inside `items`, and the `items` ones are the path operands, so `cli.find`, `cli.cp` and `cli.ls` had no callable form from a JS consumer at all. Carrying the fact as `x-apexe-path: true` — the convention already used by `x-apexe-flag` and the placement keywords — keeps the information and cannot be mistaken for an assertion by any consumer. `format: "uri"` is registered and is unchanged. The apcore-js half is a separate upstream matter; this fix stands on its own, since apexe should not have been emitting an unregistered format keyword either way.
- **An ACL rule that protects nothing now says so.** ([#39](https://github.com/aiperceivable/apexe/issues/39)) Two ways to write one silently: a deny rule naming `cli.git.cat-file` (the pre-#19 hyphenated id), `cp`, `ls` or `git log` matched no module and all four ran, because the ACL matches `module_id` and nothing else — not `metadata.command_path`, not the MCP alias; and apcore rejects an *omitted* `targets` key but accepts `targets: []`, so an empty list is inert. `build_executor` is the first point at which the policy and the surface it guards both exist, so validation happens there, against the modules actually registered (i.e. after `--prefix`/`--tags`). The refuse-vs-warn split follows what the operator can have meant: an inert rule, and a target that is a near-miss of a registered id, refuse to start — the same fail-closed rule `--acl` already applies to a missing or malformed file. A glob that matches nothing *today* only warns, because an ACL shared across differently filtered servers is a legitimate reason for it.
- **Both transports report which apexe a client is talking to.** ([#35](https://github.com/aiperceivable/apexe/issues/35)) The A2A agent card reported `"version": "0.4.1"` on apexe 0.6.0 — apcore-a2a's own stale `VERSION` constant, surfacing because `config.version` was never set — and MCP's `serverInfo.version` reported `0.17.2`, which is apcore-mcp's version. Both are now stamped from `apexe::VERSION`. The stale upstream constant remains and is not apexe's to fix; setting the field makes it irrelevant here.
- **`--show-config` carries the flags it was given.** ([#37](https://github.com/aiperceivable/apexe/issues/37)) The stdio form emitted `args: ["serve","--transport","stdio"]` regardless of `--modules-dir`, `--tags`, `--prefix`, `--acl` or `--enable-approval`, so **a user who scanned into a non-default directory got a generated config that exposed none of their tools**. `cursor` ignored `--transport` entirely and emitted a stdio command block even for `--transport http`. And an unknown format printed `Unknown config format: vscode` to *stdout* and exited *0*, so piping the command into a config file wrote that sentence as the file body — it now goes to stderr with a non-zero exit. Credential flags (`--auth-token`, `--jwt-secret`) are deliberately never echoed into a generated snippet, which is something people paste into shared repositories.
- **`--show-config` writes absolute paths.** ([#37](https://github.com/aiperceivable/apexe/issues/37)) `--show-config claude-desktop --modules-dir ./modules` emitted `"./modules"` verbatim, but the MCP client that runs the snippet launches `apexe` from *its own* working directory — Claude Desktop's is `/`, Cursor's is the workspace root — so the launched server read a directory that does not exist, logged "Modules directory not found, starting with zero tools" and exited 0. A server with no tools and no error, which is the same consequence the rest of #37.3 was filed about. A relative `--acl` failed more quietly still: the governance boundary was simply not the one requested. Every path in a snippet now goes through `std::path::absolute`, resolved against the directory `--show-config` ran in.
- **A `$not` ACL target is diagnosed by what apcore does with it.** ([#39](https://github.com/aiperceivable/apexe/issues/39)) The validator stripped the `$not` sentinel and tested the operand as if it were positive, so it reported "this rule currently protects nothing" about the exact opposite situation: apcore evaluates `$not` as `!match(operand, module_id)`, so an operand matching nothing makes the rule match *everything* — and under first-match-wins a blanket `allow` there nullifies every deny below it. A near-miss operand is worse: `$not cli.git.cat-file` against a registered `cli.git.cat_file` covers the one module it was written to exclude, and now refuses to start.
- **`--tags` refuses an empty tag instead of serving nothing.** `--tags readonly,` split to `["readonly", ""]`, and every listed tag must match — no module carries an empty tag, so the registry came up empty and the whole tool surface was uncallable, signalled only by `admitted=0` at info level, indistinguishable from an empty modules directory. Harmless before the filter moved to registration time. An empty token is now an error naming the stray comma; separately, a filter that excludes every loaded module logs a `WARN` saying so, since that case is registry-dependent and an invocation is meant to be portable across differently scanned hosts.
- **The manual shows the wire shape MCP actually returns.** §13's `isError` example rendered `exit_code`, `stdout`, `stderr` and `ai_guidance` as siblings of `isError`. apcore-mcp emits `{"content":[{"type":"text","text":"<the payload as a JSON string>"}],"isError":bool}`, so a client author following the old block read `result.exit_code`, got `undefined`, and fell back to `isError` — precisely the mistake the section exists to prevent. The example now shows the real envelope and says `exit_code` must be read after JSON-parsing `content[0].text`.
- **The F5 governance document no longer ships the inert `require_approval` ACL condition.** §9.1 of the manual was corrected in this cycle and pinned with a test; `docs/features/v2-f5-governance.md` was left behind and still showed `conditions: {require_approval: true}` in four places, one of which described it as what `generate_default` currently emits. It is not one of the five condition keys apcore registers, so a rule copied from there denies nothing under `default_effect: allow`.
- **The preview no longer discloses the binary path and argv on an ACL denial** ([#39](https://github.com/aiperceivable/apexe/issues/39)) — **fixed upstream in apcore-mcp, not here.** Listed so the three #39 items above are not read as the whole issue.
- **The manual no longer calls `--enable-approval` a "human-in-the-loop gate".** §9.6 and this changelog both already said the flag denies unconditionally and that "the docs no longer promise a prompt"; §11's limitations note was missed by that sweep. The documentation-consistency test now forbids the phrase anywhere in the manual.
- **`apexe a2a`'s lack of transport authentication is disclosed in the README too**, not only in the manual — a reader who starts from the README meets the `--auth*` flags under `apexe serve` and reasonably assumes they apply. A consistency test now checks both documents against the runtime refusal a non-loopback `--url` produces.
- **The ACL example in the manual can now match something.** ([#37](https://github.com/aiperceivable/apexe/issues/37)) §9.1's deny rule carried `conditions: {require_approval: true}`, which is not a registered apcore condition key, so apcore logged `Unknown ACL condition — treated as unsatisfied` and ran the destructive module anyway. `src/governance/acl.rs` had already documented this exact trap, removed it from `generate_default`, and pinned it with a regression test — only the docs were left behind, so anyone following the manual to lock down destructive modules got a rule matching nothing. The generated `~/.apexe/acl.yaml` was correct throughout.

### Added

- `--auth <token|jwt|none>`, `--auth-token` (or `APEXE_AUTH_TOKEN`), `--jwt-secret` (or `APEXE_JWT_SECRET`) and `--allow-unauthenticated-bind` on `apexe serve`; `McpServerBuilder::auth`. The `apexe::auth` module is public, so an embedder can supply its own `Authenticator`.
- `--no-log-arguments` on `apexe serve` and `apexe a2a`; `McpServerBuilder::log_arguments` / `A2aServerBuilder::log_arguments`.
- `--allow-deprecated-sse` on `apexe serve`; `McpServerBuilder::allow_deprecated_sse`.

### Removed

- **BREAKING (library API): `McpServerBuilder::validate_inputs`.** The library twin of `--skip-validation`, and dead for the same reason: it forwarded to apcore-mcp's pre-dispatch hook, which calls `McpExecutor::validate` — a trait method that defaults to `None` and that `ApcoreExecutorAdapter` never overrides. The method toggled nothing for either value. Deleted rather than reworded, on the grounds `--skip-validation`'s own regression test already states: failing at parse is louder than accepting a no-op that reads as "validation is off". Nothing is lost — schema validation runs in apcore's `input_validation` pipeline step inside `Executor::call`, which apexe never removes.
- **BREAKING: `apexe serve --skip-validation`.** ([#37](https://github.com/aiperceivable/apexe/issues/37)) It advertised "skip input validation against tool schemas" and skipped nothing — all 33 probes behaved identically with and without it, including the `additionalProperties`, `required`, `enum` and type violations it claimed to bypass. Every schema check runs in apcore's `input_validation` pipeline step, which apexe never removes; the flag toggled apcore-mcp's separate pre-dispatch hook, which only fires when the executor adapter implements `McpExecutor::validate`, and `ApcoreExecutorAdapter` does not. apcore does expose `ExecutionStrategy::remove("input_validation")`, so the flag *could* have been made to work — but a flag whose only effect is to unvalidate the input of a process spawner is not one worth having. Removing it is the honest end state. The argv guards were never affected either way: they live in the `execute` step.

### Changed

- **BREAKING (HTTP/SSE only):** an existing `apexe serve --transport http` deployment now needs a bearer token. stdio — how most users run apexe — is untouched. A breaking change for a security default is a defensible use of the same 0.x latitude 0.6.0 already spent on four of them.
- **`isError: false` on a non-zero exit is now documented as deliberate**, rather than left to be discovered. ([#39](https://github.com/aiperceivable/apexe/issues/39)) A wrapped command that ran and exited non-zero is a successful *call*: `grep` exits 1 when it finds nothing, `diff` exits 1 when files differ, `test` exits 1 for a false predicate, and reporting all three as tool failures would be wrong. `isError: true` stays reserved for the call never reaching the binary — schema, ACL and approval refusals. The manual now says so, with the A2A equivalent (`TASK_STATE_COMPLETED` carrying a non-zero `exit_code` in the artifact), so a client author keys on `exit_code` rather than on `isError`.

Every tool apexe served over MCP was uncallable, and most of the ones that could
be called were spelled wrong on the command line. Both are fixed here, along with
the input validation that made the two most-used wrapped tools unable to do any
real work.

A second round of verification against real binaries over `apexe serve
--transport stdio` found seven more defects, fixed here as well: every tool with
subcommands ran the wrong command, 44% of them never reached a client at all,
and the ones that did described a different command's options. Those fixes are
verified by *executing* the wrapped binary rather than by asserting on the
rendered string — three of them rendered perfectly and failed only when run.

### Fixed

- **BREAKING: the MCP tool name is the `module_id` again, so advertised tools can actually be called.** apcore-mcp lists `display.mcp.alias` as the tool name but routes an incoming `tools/call` by treating the received name *as* a `module_id` and looking it up in the registry — there is no alias-to-id reverse map anywhere on that path. apcore-toolkit's `sanitize_mcp_alias` rewrites `.` to `_`, so a dotted `module_id` — the apcore convention, and what apexe emits — guaranteed `alias != module_id` and **every tool apexe exposed failed with `[ModuleNotFound]`**, including every button in the Explorer UI. The alias is now stripped before registration, so the name in `tools/list` is the name `tools/call` accepts: `cli.curl`, not `curl`. A2A was never affected — it keeps the id and the display name in separate fields (`skill.id` / `skill.name`) — and `mcp.description` / `mcp.guidance` still apply, since only the *name* is load-bearing for routing. The upstream defect remains; this works around it without touching the `module_id` that ACL rules, `--prefix` filtering, audit records and A2A skill ids are all anchored to.
- **BREAKING: flags are spelled the way the tool actually accepts them.** The renderer prefixed every input key with `--`, which is wrong for most of what a scan finds. **452 of the 1006 flags across the 42 built-in overlays (44.9%) are short-only** and need one dash: `ls -l` was emitted as `ls --l`, which BSD `ls` rejects outright, so **45 of `cli.ls`'s 47 properties were unusable**. `find`'s `-daystart` and `-regextype` are multi-character yet single-dash, which no "one character means one dash" heuristic recovers. And `_` → `-` is lossy, so a long flag containing an underscore could never round-trip. The scanner now records the literal token it saw as `x-apexe-flag` on the schema property and the renderer reproduces it, rather than trying to invert a lossy mapping.
- **BREAKING: a long option carries its value with `=`.** It was emitted as two argv entries, which silently breaks every option whose value is *optional*: `ls --classify never` lists a file named `never` and exits 2, while `--classify=never` works. GNU spells `--classify`, `--color`, `--hyperlink`, `--backup`, `--preserve`, `--reflink` and `--context` that way, and the schema records no marker distinguishing an optional value from a required one — so `=`, which options with a required value also accept, is the only form that is always right. Short options are the opposite case and still pass the value separately, since `-I=PATTERN` would pass a value beginning with `=`.
- **BREAKING: positional arguments are passed bare, in their declared order.** All 42 built-in overlays declare `positional_args`, and every one of them was emitted as `--name value`: `ls /tmp` went out as `ls --file /tmp`. Order was lost too — nothing recorded it, so `cp source target` depended on the order the caller happened to write the JSON keys in, and `cp` inverts its meaning if the two are swapped. Operands now carry `x-apexe-positional` with their index, are emitted after all flags, and are sorted by that index. `curl` masked this in every demo: it accepts `--url` as an equivalent long option, so the one positional anybody exercised happened to work by coincidence.
- **A positional no longer silently discards a same-named flag's description.** Building the schema inserted operands last and unconditionally, so `curl`'s `<url>` operand overwrote the `--url` property and took its documentation with it. The description is now inherited when the operand has none — the common case, since usage lines carry no prose — and a name that is both required as a flag and as an operand no longer appears twice in `required`.
- **Shell metacharacters are no longer rejected in parameter values.** The 15-character blacklist was carried over from the v0.1 prototype and guarded a threat that does not exist on this execution path: arguments reach the child through `Command::args()`, which passes argv straight to `execve`, and no shell is spawned anywhere (the single `zsh` invocation in `scanner::completion` runs a hardcoded constant with no interpolation). `;`, `|`, `&`, `$`, backtick and quotes are ordinary bytes in argv — they cannot start a command, open a pipe or expand a variable. Rejecting them bought nothing and **made `curl` unable to send a JSON body (`{"a":1}`) or a form (`a=1&b=2`), and `jq` unable to receive any filter containing `|`, `(`, `)` or `$`** — that is, unable to do the only thing `jq` does. `\0`, `\n` and `\r` are still rejected: the first is refused by `Command` anyway, and the latter two corrupt the audit log's line framing.
- **Option-injection is now blocked, which the old blacklist did not do.** `-` was not in that 15-character set, so a value of `--output=/etc/passwd` or `-K /etc/shadow` passed validation and was handed to the wrapped tool's own parser, which cannot distinguish it from an option the caller was never granted. Values that begin with `-` are now rejected. This matters more after the change above, because an operand reaches argv bare with no flag token in front of it. A JSON *number* is exempt, so a legitimate negative number still works; the same thing typed as a string is not, because the caller asked for text.
- **Values from binding files keep the strict character set.** `json_flag` and `command_parts` are build-time scan artifacts, not runtime data, so nothing legitimate puts a shell metacharacter in them and the conservative check stays useful there as a tamper signal. Applying one rule to both classes was the original mistake: it imposed a build-time constraint on caller-supplied data.
- **GNU-style operands are extracted at all.** The usage-line parser only understood the BSD spelling, where the ellipsis goes inside the brackets (`ls ... [file ...]`). GNU puts it outside and writes required operands bare and in caps, and **all 20 GNU tools checked spell them that way**: `ls [OPTION]... [FILE]...`, `cp [OPTION]... [-T] SOURCE DEST`, `mkdir [OPTION]... DIRECTORY...`, `grep [OPTION]... PATTERNS [FILE]...`. Not one of those forms matched, so every GNU tool without a curated overlay produced a contract with no operands — an agent reading it had no way to name the file to operate on. Both ellipsis placements and the bare all-caps form are now recognised. Two exclusions keep this from over-reporting: `[OPTION]...` and `cut`'s bare `OPTION...` name the option group rather than an operand, and a bracketed group whose first character is `-` is options all the way through — which is what separates `[FILE]` from `[-T]`, `[-Olevel]`, `[-D debugopts]` and BSD's bundled `[-@ABCF]`, where the capitals sit behind a `@` rather than behind the dash. Verified against usage lines read from GNU coreutils 9.7, grep 3.11, diffutils 3.10 and findutils 4.10.0 in the digest-pinned image the overlays' own provenance names.
- **`jq`'s filter — its only required argument — is now extracted.** The usage-line parser required a placeholder name to be a single token, so `jq [options] <jq filter> [file...]` yielded nothing at all and the generated module could not filter anything. Multi-word placeholders are now read (`<jq filter>` → `jq_filter`), and bracketed variadic operands (`[file...]`) are recognised alongside the angle-bracket form. The trailing `...` is required for the bracketed form, which is what stops it from reading `[options]`, `[-l]` or `[--color=when]` as operands — the same restriction the BSD parser has always carried. Both styles are returned in usage-line order, since order is the argument's meaning.
- **Subcommand modules ran the tool name twice (`git git log`).** ([#17](https://github.com/aiperceivable/apexe/issues/17)) The target was built by prefixing the binary path onto `full_command`, which already carries the tool name, so `cli.git.log` emitted `exec:///usr/bin/git git log` and every call came back with `git: 'git' is not a git command`. It affected **every tool that has subcommands** — all 142 `cli.git.*` and all 12 `cli.cargo.*` modules on the reporter's machine. The target is now built from the subcommand path alone. The old shape was pinned as correct by a unit test asserting `"exec:///usr/bin/mytool mytool list"`, forty-six lines above another test whose comment reads *"Root-only target should NOT repeat the tool name as an argument"* — the duplication was recognised on one branch and asserted on the other, which is how it survived the release. That assertion is corrected, and the new coverage executes the module rather than comparing strings: a target that renders is not a target that runs.
- **Hyphenated `module_id`s were written, counted, and then silently dropped.** ([#19](https://github.com/aiperceivable/apexe/issues/19)) apcore enforces `^[a-z][a-z0-9_]*(\.[a-z][a-z0-9_]*)*$` at *registration*, but ids were derived straight from the command name, so `git cat-file` produced `cli.git.cat-file`. `apexe scan` wrote it, `apexe list` reported "142 module(s) found", and the server then refused it with a warning on stderr — **63 of git's 142 subcommands (44%) never reached a client**, and nothing on the success path said so. The charset is now applied at generation time, so the surface a scan reports and the surface a server serves are the same set. The mapping is lossy and one-way, so the real command name is preserved in `metadata["command_path"]` — the hyphen is what argv needs. A unit test asserting that Unicode names survive *into* the id was pinning the same defect (`cli.café.état` is exactly as unregistrable) and now asserts the id is registrable and the name is preserved beside it.
- **Subcommand contracts described the wrong command.** ([#18](https://github.com/aiperceivable/apexe/issues/18)) `git log --help` does not print help — it runs `man git-log`. No Tier 1 parser recognised that shape, so the parse yielded nothing and the module was assembled from the *tool's* global flags alone: all 25 of `cli.git.log`'s properties were `--git-dir`, `--paginate`, `--html-path` and friends, and `{"oneline": true}` was rejected as invalid input. A new `Man` parser reads the man-page layout at Tier 1 using the machinery Tier 2 already had, so a subcommand finally describes itself: `cli.git.log` now carries **111 properties including `--oneline`, `--follow` and `--max-count`**, plus the `<revision-range>` and `<path>` operands recovered from the SYNOPSIS, which were previously inexpressible. Four classes of malformed property name are fixed with it, all of which produced keys no caller could render back to a flag: `--exec-path[=<path>]` yielded `exec_path[`, `--[no-]verify` yielded `[no_]verify`, `-n<num>` yielded `n<num>`, and the end-of-options marker `--` yielded a property whose key was the empty string. A real scan of git now produces **zero unregistrable ids and zero malformed property names** across all 142 modules. The bracket that marks an optional value is recorded rather than discarded, since it is the only thing distinguishing `--exec-path` from `--exec-path=<p>`, and such a flag's schema now admits both spellings.
- **Options that take a value were typed `boolean`, and swallowed the next flag.** ([#21](https://github.com/aiperceivable/apexe/issues/21)) When a placeholder was spelled in a form the format's regex did not anticipate — `--proxy [protocol://]host[:port]`, or a value separated from its description by one space rather than two — it fell into the description text and the flag was typed boolean. Both doors were then shut: the schema permitted only `true`, and `true` rendered a bare flag the binary rejects. Worse, a bare value-taking flag is not a no-op — `{"proxy": true, "connect_timeout": true}` rendered `--proxy --connect-timeout` and curl dialled a proxy named `--connect-timeout`, which is the same "it runs, and honours something the caller never meant" failure `x-apexe-conflicts-with` exists to prevent, reached from the renderer's own output. Affected **11 of `cli.curl`'s 257 properties and 3 of `cli.ssh`'s 45**, including every form of ssh port forwarding. A placeholder left at the head of a description is now recovered and the property retyped, in a pass shared by every parser rather than fixed one regex at a time. The renderer additionally refuses to emit a bare token for an option the schema says takes a value.
- **`find`'s predicates rendered before the path, which no `find` accepts.** ([#20](https://github.com/aiperceivable/apexe/issues/20)) Operands were emitted after every flag unconditionally. `find`'s grammar is `find path ... [expression]`, so `find -name '*.txt' dir` is rejected outright — "illegal option -- n" on BSD, "paths must precede expression" on GNU — making **all 98 predicate properties of `cli.find` unusable**. Operands now carry a placement marker (`x-apexe-operand-position`), and each side of the flags keeps its own declared order, since `find` has one operand on each side. Placement is not derivable from a scan: the usage line gives the operand order but never says which of a tool's options live inside the trailing operand slot — find's predicates are documented in PRIMARIES, not in the synopsis — so it is stated in an overlay or not at all, and a tool without one keeps the ordinary trailing-operand behaviour. Set on `find@bsd` and `find@gnu`, both checked behaviourally against the real binaries (macOS 26.3 `/usr/bin/find`, and findutils 4.10.0 in the digest-pinned image `find@gnu`'s own provenance names).
- **The circuit breaker counted caller mistakes as module failures.** ([#22](https://github.com/aiperceivable/apexe/issues/22)) apcore's breaker feeds every `ModuleError` into its rolling window, which inverts the polarity for a module wrapping a CLI binary: five calls rejected by *input validation* — the binary never spawned — opened `cli.ls` for every caller, while five calls where `ls` really did fail on a missing path left it closed, because a non-zero exit is a successful execution. So a tool that failed every time kept its circuit closed while a caller sending a schema-invalid object disabled it for everyone. That collides directly with apexe's audience: schema trial-and-error is the normal behaviour of an LLM caller, and an agent that reads a conflict refusal and corrects itself is the *success* case for the `conflicts_with` enforcement added in this same release. Only failures that say something about the dependency's health — spawn failure, timeout, signal death — now feed the breaker. Governance refusals are excluded too, so a denied caller cannot open a circuit shared with the callers an ACL allows.
- **`documentation` embedded raw man-page overstrike sequences.** ([#23](https://github.com/aiperceivable/apexe/issues/23)) Help text captured from a tool that delegates `--help` to its man page was stored verbatim, so each `cli.git.*` binding carried `g\bgi\bit\bt l\blo\bog\bg` where it meant `git log` — **2.4 MB for a single git scan**, largely encoding, and unreadable as documentation for the agent that reads it. Overstrike is now collapsed at the point of capture.

### Changed

- **Existing bindings keep working, but need a rescan to benefit.** Every schema keyword introduced in this release is optional, and its absence preserves the prior behaviour: the renderer falls back to the old `--{key}` spelling for any property without the new annotations, so bindings generated before this release behave exactly as they did rather than silently emitting nothing. Re-run `apexe scan` to pick up the corrected flag forms, targets, registrable ids, subcommand contracts and operand ordering.
- **`ln` is annotated `destructive`.** `ln -f` unlinks an existing target before linking, discarding that file's directory entry irrecoverably — the same overwrite behaviour for which `cp` and `mv` are already marked destructive, and the reason GNU `ln` offers `--backup`. Verified against the binary rather than inferred.
- **A man-page placeholder now types the value it names.** `--max-count=<number>` was typed `string`, so the `3` a caller naturally sends was rejected. Inference is deliberately narrow — an unrecognised placeholder stays a string, because a wrong numeric guess rejects a value the tool accepts.

### Fixed (overlays)

- **`ls@gnu`: `-F` / `--classify` takes an optional value.** It was typed `boolean`, so `ls --classify=never` could not be expressed at all under `mode: authoritative`. GNU coreutils 9.7 spells it `--classify[=WHEN]` and rejects `--classify=bogus`; it is now an `enum` over `always`/`auto`/`never`, matching how the same file already handles `--color` and `--hyperlink`. Verified in the digest-pinned image the overlay's own provenance names.
- **`ls@gnu`: `-f`, `-c` and `-u` described behaviour coreutils 9.7 does not have.** `-f` was documented as `disable -ls --color`, which stopped being true years before the 9.7 the overlay claims to describe: `ls -l -f` produces a full long listing and `ls -f -s` prints block counts. GNU 9.7 says only `same as -a -U`. `-c` and `-u` were flattened to `Sort by, and with -l show, ctime` — but the real behaviour is three-way, and the flattened form asserts the opposite of one branch: `ls -lc` sorts **by name**, not by ctime (only `-lt` sorts by it). All three now carry GNU 9.7's own wording, verified against the binary.
- **`find@gnu`: `-prune` was described as false under `-depth`.** It said `Always true unless -depth is in effect`; GNU's man page says `True; ... If -depth is given, then -prune has no effect`, and `find /p/sub -depth -name sub -prune -print` does print, proving the predicate still evaluates true. An agent reading the old text would invert the short-circuit in the standard `-prune -o -print` idiom.
- **`diff@gnu`: `--forward-ed` had its ordering backwards.** It claimed output `in the ed command order, which ed cannot itself digest`. Per diffutils' own manual the forward form carries changes *in the order they appear in the file*; it is `-e`, the form ed *can* digest, that is reversed. The old phrasing was also a reworded BSD man-page line.
- **`sort`: an unattributable claim, present in two variants.** Both `sort@gnu` and `sort@apple` ended `--output` with `The file is truncated and rewritten.` — a sentence in no GNU help, man page or texinfo, and in no macOS man page either. It also implies the opposite of a documented guarantee: sort reads all input before opening the output file, so `sort -o F F` sorts in place, which both variants do. Replaced on the GNU side with the texinfo fact, dropped on the Apple side.
- **`grep@gnu`: `--colour` carried BSD's wording.** `The same as --color` is BSD grep's man page; GNU's help lists `--color[=WHEN], --colour[=WHEN]` as a single entry and never says it.
- **`cp@gnu`, `mv@gnu`, `ls@gnu`: optional values are now stated consistently.** `--backup`, `--preserve`, `--reflink`, `--context`, `--classify` and `--hyperlink` all take an optional value, and only some said so — `cp --context` and `mkdir --context` are the same flag with the same GNU help text, and one documented it while the other did not. `ls --hyperlink` additionally read `Hyperlink file names.`, dropping the `WHEN` its own `value_name` and `enum_values` declared.
- **`chmod@bsd`: `mode` is not always required.** BSD `chmod`'s second usage form — `chmod [-fhv] [-R [-H | -L | -P]] [-E | -C | -N | -i | -I] file ...` — takes an ACL option in place of a mode operand, and `chmod -C <file>` parses fine without one. Marking it required blocked the entire ACL usage form.

### Added

- **`conflicts_with` reaches the generated contract, and a conflicting call is refused.** The field that `docs/overlays.md` calls the single biggest reason overlays exist had no consumer: 42 built-in overlays declare mutual exclusion on 220 flags, and `build_input_schema` never emitted any of it, so not one reached a binding. It is now written to each property as `x-apexe-conflicts-with` — translated from command-line spellings into the property names a caller actually sends — and the executor refuses an invocation that names both.

  Refusing matters more than reporting. Without it the pair is not an error but something worse: it renders, and *which* of the two the tool honours is decided by the order the caller happened to write the JSON keys in. An object has no ordering anyone intended as an interface, so `{"f": true, "i": true}` on `rm` was never "interactive wins" — it was whichever key was typed last. The call now fails with a message naming both flags, identically whichever order they arrived in.

  `false` and null still render nothing and so do not count as sending a flag: `{"l": true, "1": false}` remains a valid way to say "long listing, not single-column". Only curated overlays state mutual exclusion, so a schema without the annotation is unaffected.

### Changed (overlay format)

- **175 mutual-exclusion pairs added across 22 overlays.** Once the definition widened and the executor began enforcing it, the overlays that had recorded only diagnosed errors were left with real gaps — a group the binary resolves silently is exactly the one a caller cannot predict, so it is the *more* important of the two to declare. Every pair was run in both orders against the reference build named in that overlay's own provenance (BSD/apple on macOS, GNU in the digest-pinned image) and kept only where the outcome depends on that order, or where one side is silently discarded. Biggest gaps: `ls@gnu` +45 (sorting, timestamp source, quoting style, indicator style, size units — seven separate dimensions, of which only output format had been recorded), `df@bsd` +22 (the seven-way block-size group its SYNOPSIS spells with `|`), `grep@gnu` +15 and `grep@bsd` +11 (output modes had been declared against `-n` but never against each other), `du@gnu` +13, `df@gnu` +10, `diff@gnu` +10 (`-q`/`--brief` overrides every output style silently, which is why it escaped the group everything else was diagnosed into).

  Same-named flags diverge between variants more than expected, and each side was derived only from its own evidence: `wc -c -m` overrides on BSD but prints both columns on GNU; `uniq -d -u` lets `-d` win outright on BSD while GNU yields the empty set identically in either order; `rm -i -I` coexists on BSD but is last-one-wins on GNU; `sort -c -m` is diagnosed by Apple's build and accepted by GNU's, and `-c -o` the other way round. Four pairs were tested and deliberately *not* declared, since a wrong entry now refuses a legal call: `tail@bsd -f/-F` (`-F` implies `-f`), `grep -o/-n` (both take effect), `rm@bsd -i/-I` (both prompts fire), `df@gnu -P` (not part of the block-size dimension). The `provenance.notes` in every touched file record which kind each group is, and sentences written under the older narrow reading were corrected rather than left to contradict the data.
- **`conflicts_with` covers override groups, not only diagnosed errors.** The 42 built-in overlays had been split between the two readings, so the same field meant different things in different files. It now means "these must not be sent together" in both senses, and the reason is specific to how apexe is called: its input is a JSON object, which has no ordering, so for a last-one-wins group *which* flag wins is decided by the order the caller happened to write the keys in. `{"f": true, "i": true}` on `rm` is not "`-i` wins", it is unpredictable — the same one correct move as for a hard conflict, namely send one or the other. The narrower reading is actively worse here: it marks such a pair as combinable, which tells an agent it may send both. `du@bsd`'s note, which had stated the opposite rule, is corrected; `provenance.notes` is now where the *kind* of incompatibility is recorded.
- **`provenance.source` is documented as the document read, not the check performed.** No `binary-probe` value was added, and the reasoning is written down so it is not revisited by guess: probing establishes that a flag exists, what the binary prints on rejection, and whether a value must be attached — but not what a flag *means*, which is what a description asserts and what `source` attributes. `ls@gnu`'s `-f` is the case in point: `--help` was right the whole time and the description was stale, so the probe's role was to send someone back to the document. Probe findings belong in `notes`, with the command that produced them.

### Documentation

- The built-in GNU overlay count in `docs/overlays.md` said 14; there are 21, and four of them declare `GNU diffutils` / `GNU grep` / `GNU findutils` rather than `GNU coreutils`.
- **Every `provenance.command` that names a container image now pins it by digest.** Twenty GNU overlays ran `docker run --rm debian:stable-slim <tool> --help` while their `environment` pinned a digest — a self-contradiction that would have re-read a different build on any later run. `docs/overlays.md` now says so explicitly, since it already required a digest for `environment`.
- The basic example advertised flag counts that no longer matched what a scan produces (`curl — 12 flags`, against 257 actually found) and suggested a `cli.curl` call with no `url`, which cannot succeed. Its sample calls now run, and it states that Explorer prefills every schema property as a blank template that has to be trimmed before calling — an empty string is a value, not an omission, and `curl --output ""` fails on it.

### Fixed (self-review of the above)

Seven defects the fixes above introduced, each found by reviewing this release
against real binaries and each verified by re-running the failing case. They are
listed separately because every one of them is a regression created by a fix in
this same release, not a pre-existing bug.

- **The circuit breaker's error filter disabled a module in the half-open state.** Not counting a caller-fault error is not the same as the call never happening. In `HALF_OPEN` apcore admits exactly one probe and releases the slot in only two places — `after` on success, and the `on_error`-that-opens branch, which in that state is *every* `on_error`. Returning early therefore skipped the only release path the call had, and because apcore runs middleware `before` *ahead of* input validation, one invalid argument object was admitted as the probe and then rejected, leaving the slot held. Every other caller was refused with `CircuitBreakerOpen` for a full 30-second recovery window: the exact defect #22 exists to remove, relocated from `CLOSED` into `HALF_OPEN`. The suppressed path now hands the slot back, leaving the rolling window untouched so a caller mistake still cannot launder an unhealthy dependency back to `CLOSED`.
- **Operand placement broke `find`'s options while fixing its predicates.** `find` puts two classes of dash-token on opposite sides of the same operand — options before the paths, primaries after — and `before_flags` is a single boolean on the operand, so it moved both at once. `find dir -L` is "unknown primary or operator" on BSD and "unknown predicate" on GNU, so 8 BSD and 6 GNU properties went from working to broken while the 88 primaries went the other way. Placement is now expressible per flag as well (`before_operands` → `x-apexe-flag-position`), and the renderer emits four ordered groups: leading flags, leading operands, trailing flags, trailing operands. Each of the 14 options was run in both positions against the builds the two overlays' provenance names; `-d` was tested and deliberately left unmarked, because BSD accepts it either way.
- **`apexe scan --format json` reported command lines that do not run.** The id fold is one-way, and `CommandContract.command` still reverse-derived from the id, so **68 of git's 142 commands** were reported as `git check_ignore`, `git cherry_pick`, `git format_patch` — strings git rejects. `metadata["command_path"]`, added in this release precisely to hold the unfolded name, had no reader. The field is now built from it, falling back to the id only for bindings written before that key existed.
- **The placeholder-recovery pass re-typed working boolean switches.** It accepted any first token containing brackets and any ALL-CAPS first word, neither of which is reliably a placeholder: Info-ZIP prefixes **16 boolean switches** with `[WIN32]` / `[VMS]` / `[MacOS]`, `[deprecated]` is a widespread convention, and descriptions open with a caps identifier (`ld -noprebind` — "LD_PREBIND is no longer supported"; `ex --echo-wid` — "GTK GUI only:"). Each became a value-taking string option that could no longer be sent as `true` at all — the inverse of the bug the pass was written for. The bracket form now requires text *outside* the brackets, which is what distinguishes `[protocol://]host[:port]` from a tag, and the bare-caps form is restricted to a closed list of conventional operand words.
- **`--time-cond` was typed as a number.** `contains("time")` matched as a substring, so curl's `-z, --time-cond <time>` — which takes a date expression or a filename — admitted only values curl cannot use. Durations are now matched as whole words.
- **The end-of-options fix did not actually drop the flag.** `parse_flag_line` skipped *naming* a bare `--` but still returned a flag, so it reached the schema through `canonical_name`'s `"unknown"` fallback: **6 of git's 142 modules** advertised a boolean property named `unknown` that renders as `--unknown`, which git rejects. Nameless flags are now dropped at the single point every parser path funnels through. The regression test passed throughout because it asserted the name was non-empty, which the fallback satisfies; it now asserts the count.
- **Man-page synopses leaked option letters and option values as operands.** A synopsis spells an alias set as a parenthesised alternation — `[(-m | --max-count) <num>]` — so the character after `[` is `(` rather than `-` and the group read as operands, and the check ran only on the innermost bracket. `cli.git.grep` declared `o`, `pager` and `num` as positionals, and on `cli.git.commit` an operand named `c` **displaced git's real `-c` option**, making it unreachable. The option-group check now skips a leading `(` and walks outward through every enclosing group, and the angle-bracket pass consults it at all — which it never had, because ordinary `--help` text writes `[-C <path>]` and never exposed the gap.

A rescan of git now produces 142 modules with zero unregistrable ids, zero malformed property names, zero bogus `unknown` properties, zero non-invocable command strings, and `-c` restored as a flag.

### Changed (self-review of the above)

Eight further findings from the same review. None is a wrong answer to a caller,
so they are listed apart from the defects above.

- **An existing cache silently bypassed every scanner fix.** The cache key named only the tool, variant and version, so it did not change when apexe's own parsing did — and because every field added to the scanned model is `#[serde(default)]`, a document written by an older build still deserialized and was returned before any parsing ran. A user who upgraded and re-ran `apexe scan git` got the pre-fix result at exit 0 with nothing saying so, and `--no-cache` was the only escape. The key now carries a `SCAN_FORMAT_VERSION`, bumped to 2 for this release.
- **A positional operand no longer erases a same-named flag.** "Operand wins" is right for `curl`, where `--url` and `<url>` are the same thing, but `find -path PATTERN` is a glob predicate unrelated to the `path` operand, and `grep --file=FILE` reads patterns from a file while the `file` operand names what to search. Both options had vanished from their contracts entirely. The displaced flag is now re-keyed (`path_option`, `file_option`) rather than dropped; the executor spells a flag from `x-apexe-flag`, never from the property key, so the rendered command line is unchanged.
- **Accurate subcommand summaries are no longer padded with the parent tool's description.** Appending the tool's man DESCRIPTION to any subcommand summary shorter than 20 characters made sense while those summaries were stubs. Once the man parser started supplying real NAME lines, `git log` → "Show commit logs" became "Show commit logs — Git is a fast, scalable, distributed revision control system…", 84% of which describes `git` — the same "description of git filed under the name of git log" the man parser exists to prevent. A summary that came from a man page is now left alone.
- **Scanning by absolute path yields the same contract as scanning by name.** `ManHelpParser` forwarded the raw `tool_name` to example extraction, which matches a bare invocation by prefix — so `/usr/bin/git` matched no EXAMPLES line and the same tool produced different output depending on how it was named.
- **One placeholder-to-type table instead of four.** `parsers::gnu`, `parsers::clap_parser`, `parsers::click` and the new recovery pass each carried their own, and they disagreed: `SIZE` was String in one and Integer in another, `FLOAT`/`DECIMAL` existed only in the GNU copy, durations only in the new one. Both the help path and the man path feed the same merged flag list, so an option's emitted JSON type depended on which parser happened to win on that host — `{"size": 4096}` validated against one machine's contract and was rejected by another's.
- **The circular dependency between `scanner::man_page` and `scanner::parsers` is gone.** `value_placeholder` is a post-parse repair pass with consumers on both sides of the tier boundary, not a `CliParser`, so it now lives at `scanner::value_placeholder`.
- **`value_optional` is declarable and documented.** It reached the Rust overlay loader and the emitted contract but never `$defs/flag` in `schemas/tool-overlay.schema.json`, which is `additionalProperties: false` — so an author writing it got a validation failure for a field the loader honours, and the field appeared in no document. Both are fixed, and `before_operands` was added to the schema alongside it.
- **BREAKING (library): one unscannable tool no longer discards the whole batch.** `ScanOrchestrator::scan` propagated the first error with `?`, so `apexe scan git curl nonexistent` wrote *no* bindings at all — the tools already scanned were thrown away, the tools after it were never reached, and the message named no tool. Scanning is per-tool work with no shared state, so there was nothing to abort for. It now returns a `ScanOutcome { tools, failures }` instead of `Result<Vec<_>>`; each failure carries the tool as the caller named it and the rendered cause. The CLI writes bindings for everything that scanned, names every failure, and still exits non-zero — reporting `Scanned 21 of 22 tools` with the successes on disk, because a pipeline must not read a short surface as the whole surface. A run where *nothing* scanned fails outright and writes nothing, since an empty ACL over a good one is worse than doing nothing.
- **Array-typed paths and URLs carry their `format` hint again.** The hint exists so an agent can tell a path from free text, but it was attached inside the scalar branch of each schema builder, so both array branches dropped it — and arrays are the common case for exactly those types. Scanning ten of the overlay-backed tools recovers 12 hints that were previously emitted for none of them. It is attached to `items`, where it describes each element rather than the array, and `format_hint` is now the one place that decides it.
- **Documentation that this release invalidated.** The parser inventory was stated in four places and only `FEATURE_MANIFEST.md` was guarded, so the user manual still said "Five", and the README and the scanner's crate doc still listed the four parsers from before BSD Usage existed. §9.5 of the manual still described `CircuitBreakerMiddleware` counting every failure — the behaviour this release removes. All four sites are corrected and the doc-consistency test now covers the manual, the README and the crate doc, so the next parser cannot go stale in one file only.


### Known gaps

- **The negated half of `--[no-]verify` is not listed separately.** The notation documents both `--verify` and `--no-verify`; the parser emits one flag per option line, and the affirmative form is what it keeps. Manufacturing the second flag is a change to that contract rather than a fix to a malformed name, so it is left for its own change.

## [0.5.1] - 2026-07-28

### Fixed
- **A global option's value placeholder is no longer scanned as a positional argument.** Usage lines spell an option's argument with the same `<name>` angle brackets as a real operand, and the extractor took every `<name>` on the line — so `usage: git [-v | --version] [-h | --help] [-C <path>] [-c <name>=<value>]` gave `git` three *required* positional arguments named `path`, `name` and `value`, none of which the bare command accepts. An agent reading that contract would construct a call `git` rejects. Placeholders bound to an option (`-C <path>`, `-c <name>=<value>`, `--git-dir=<path>`, `--exec-path[=<path>]`, and repeatable forms like `--include=<path>...` and `-I <dir>...`) are now skipped, and a placeholder inside an optional `[...]` group reports `required: false` instead of the hardcoded `true` — the trailing `<args>` in `git [--version] <command> [<args>]` is optional by construction.
- **The four help parsers share one usage-line extractor.** `gnu`, `cobra`, `clap` and `click` each carried a verbatim copy of the same naive regex, so the defect was present in all of them and a fix to one would have left three behind. They now call `scanner::parsers::positional_args::extract_args_from_usage_line`. The BSD parser already avoided this class of mistake (its `BUNDLED_RE` documents why valued options must not match) and is unchanged. Overlays are unaffected — they carry no subcommand layer and never took this path.

## [0.5.0] - 2026-07-28

### Added
- **Man page `EXAMPLES` are extracted** — `ScannedCLITool.examples` and `CommandContract.examples` now carry the hand-written invocations from a tool's man page: `ls` yields 3, `find` 9, `tar` 10 and `grep` 13, where every tool previously yielded 0. This is the only human-reviewed usage a scan can reach — help text lists what the flags *are*, while `EXAMPLES` shows which combinations make sense together, and no amount of flag parsing recovers that. Both man layouts are matched: a shell prompt (`$ grep -w 'patricia' myfile`, used by `ls` and `grep`) and a bare invocation (`tar -czf file.tar.gz source.c`, used by `tar` and `find`). A bare invocation is accepted only when it starts with the tool's own name, which is what separates a command from the prose describing it — every one of these pages interleaves the two. Kept as command lines rather than parsed into structured inputs, deliberately: `find / \! -name "*.c" -print` does not survive being parsed back into schema fields, and a consumer that guessed at one would emit a call the tool rejects.
- **`CommandContract.examples`** — the flattened contract dropped the examples the generated binding carried, so one scan described the same command differently depending on which output a consumer read.
- **Prebuilt release binaries** — a GitHub Actions workflow (`.github/workflows/release.yml`) now builds `apexe` for `x86_64`/`aarch64` on both macOS and Linux and attaches the archives (plus `sha256` checksums) to the GitHub Release, so installing no longer requires a Rust toolchain. It runs on the `rust/v*` tag that `apdev-rs release` pushes, or can be dispatched manually against an existing tag to backfill binaries. `aarch64-unknown-linux-gnu` builds natively on GitHub's `ubuntu-24.04-arm` runner rather than cross-compiling, avoiding a `pkg-config` cross-compilation sysroot that isn't set up on the `x86_64` runners.

### Changed
- **Linux release builds statically link OpenSSL** — `Cargo.toml` now pulls in `openssl` with the `vendored` feature for `cfg(target_os = "linux")`, so the released Linux binaries no longer depend on whatever OpenSSL version happens to be installed on the end user's distro.

### Fixed
- **BREAKING: `open_world` is inferred rather than asserted.** It was hardcoded `true` for every command, which left the annotation carrying no signal at all: `ls` and `curl` were indistinguishable, `risk_from_annotations` had to ignore the field (its own doc comment said so), and **`Risk::OpenWorld` was therefore never emitted by any scan** — a declared risk class no output could contain. A consumer gating on the boundary (demanding a declared credential, or refusing to run a networked command in a local sandbox) had nothing to gate on. Two signals now: the executable itself (`curl`, `wget`, `ssh`, `scp`, `sftp`, `rsync`, `nc`, `telnet`, `ftp`, …), and networked subcommands of otherwise local tools (`push`, `pull`, `fetch`, `clone`, `publish`, `install`, `deploy`, `login`, …). `git` scans to 4 `open-world`, 7 `readonly`, 127 `write` and 4 `destructive` commands where every one was previously alike. Name-based, so it is a floor rather than a guarantee — a tool that opens a socket under an unremarkable name is not caught, and an overlay's `annotation_overrides` remains the way to state the truth for a specific one.
- **BREAKING: `risk` consumes `open_world`.** `curl`, `wget` and `ssh` report `open-world` where they reported `write`. Destructive outranks open-world, because irreversibility is what a consumer must gate on first; open-world outranks readonly, because `curl` reading a URL still crosses a trust boundary, and reporting it as readonly hides it from the gate that exists for exactly that.
- **`--format` and `-j` no longer imply JSON output.** The structured-output regex fallback matched a bare `--format` or `-j` anywhere in help text, so `tar` was tagged `structured-output` — telling an agent it could request JSON from a command that has never emitted any. `tar --format` selects an archive format (`ustar`, `pax`, `cpio`) and `tar -j` selects bzip2 compression. Every pattern now requires the word `json` on the same line as the flag, which keeps the Cobra-style `--format string   Output format (json, text)` matching while dropping `tar`'s bare `--format <format>`. `-j` is removed entirely: across CLIs it means "jobs" or "bzip2" far more often than JSON.

## [0.4.0] - 2026-07-28

### Added
- **Tool variant detection** — a command name does not identify a program, so every scan probes the binary (`<binary> --version`) and classifies it as `bsd`, `gnu`, `apple`, `busybox` or `unknown`, surfaced as `ScannedCLITool.variant`. macOS `/bin/ls` is BSD, Linux `/usr/bin/ls` is GNU coreutils, Alpine is BusyBox, and Homebrew coreutils puts GNU `ls` on a macOS box — the probe is the only signal that separates that last case from the system binary, so no path heuristic can replace it. `gnu` spans the whole GNU family rather than coreutils alone, since `diffutils`, `tar`, `sed` and `bash` are separate projects; `apple` covers Apple's own ports, whose banner names Apple rather than BSD (`sort` reports `2.3-Apple (197)`, `git` reports `(Apple Git-155)`).
- **The classification order is fixed and load bearing.** Six rules run in sequence: `busybox`, a BSD marker, a `GNU <package>` pair, an Apple marker, a rejected `--version` corroborated by a BSD-family platform, then `unknown`. **BSD is tested before GNU** because macOS `grep` reports `grep (BSD grep, GNU compatible) 2.6.0-FreeBSD` — a BSD tool advertising GNU compatibility, not a GNU tool. The Apple rule strips `<arch>-apple-<os>` target triples first, since `curl 8.7.1 (x86_64-apple-darwin25.0)` and `GNU bash ... (arm64-apple-darwin25)` both carry the token without being Apple ports. Licence boilerplate is excluded from the GNU test, because every GPL tool prints `GNU General Public License` whether or not it is a GNU project. A `bsd` verdict from a *rejected* probe additionally requires platform corroboration: rejecting `--version` only proves a tool is not GNU. BSD markers match token *prefixes*, so `bsdtar 3.5.3 - libarchive` classifies as BSD. The reasoning is recorded in `docs/overlays.md` so the order is not "simplified" later.
- **Curated tool overlays** — a reviewed description of one variant of one command, keyed by `(command, variant, version_range)` and matched by `probe` > `platform` + `binary_globs` > `platform` alone. `mode: authoritative` replaces the scan surface entirely (for system built-ins the overlay fully enumerates); `mode: merge` keeps the scan as the base and overrides matching flags. Overlays are the only source that can state `conflicts_with`, since no help or man page format expresses mutual exclusion machine-readably. **42 ship built in**, covering the 21-command POSIX core across their BSD, GNU and Apple variants — `cat chmod cp cut df diff du find grep head ln ls mkdir mv rm sort tail touch uniq wc xargs`; `~/.apexe/overlays/*.{json,yaml}` and `apexe scan --overlay <PATH>` add more. The format is defined by a standalone JSON Schema at `schemas/tool-overlay.schema.json`, with tests guarding it against drifting from the Rust types.
- **Overlay provenance is mandatory at `confidence: verified`** — an overlay claiming to be verified must record how it was checked: the platform and version of the reference installation, the upstream `package`, which document was read (`man-page` / `help` / `vendor-docs`), the date, and ideally the re-runnable command and a digest-pinned environment. The schema rejects a `verified` overlay without it, and `vendor-docs` additionally requires a `reference` citation because it has no command anyone can re-run. Without this, a `verified` + `authoritative` overlay replaces the entire scan result with an assertion nobody can re-check. `EvidenceSource` has exactly three variants by design — there is none meaning "I know this tool", because that is not evidence.
- **Per-flag `confidence` and `sources`** — every `ScannedFlag` records which tiers produced it, plus a derived trust level: `verified` (overlay) > `high` (completion spec) > `medium` (two independent heuristic sources agree) > `low` (a single unconfirmed source). Consumers can now tell a curated fact from a text-scraping guess. On macOS, `ls` reports 46 `verified` flags; `curl` reports 12 `medium` and 245 `low`.
- **`ScannedCLITool.positional_args`** — tool-level positional arguments (`ls [file ...]`) now reach the generated input schema through the synthesized root command. Tier 1 parsed them and then discarded them.
- **Overlay behavioral annotations** — an overlay may assert `readonly` / `destructive` / `idempotent` / `requires_approval`, overriding the adapter's name-and-flag inference. Only fields the overlay actually sets are replaced.
- **Man pages promoted to a first-class usage source** — Tier 2 now contributes flags to `global_flags`, not just descriptions to flags Tier 1 already found. Tools whose `--help` is a single bundled usage line (most BSD/macOS built-ins) previously scanned to zero flags: on macOS, `ls` now yields 46 flags (was 0), `grep` 51 (was 0), `git` 25 (was 0), `curl` 257 (was 12).
- **BSD man page layout support** — options listed inside `DESCRIPTION` are parsed, in addition to the GNU `OPTIONS` section. The intro line is matched as a pattern (`the … options are as follows/available`) rather than a fixed list, because the wording varies per page and the variants arrived one bug at a time: `ls` says "The following options are available", `cat` "The options are as follows", `sort` "The command line options are as follows", `chmod` "The generic options are as follows". Missing one is silent — the entire option block simply becomes invisible, which cost `sort` 10 flags and `chmod` 4 before this was generalized. Option indentation is inferred from the first option line instead of being hardcoded to GNU's 7 columns (BSD uses 5).
- **Man page flag detail** — alias lists (`-a, --all`), inline values (`--color=when`), and separate value placeholders (`-D format`, `-o FILE`) are parsed, so value-taking flags map to `string` and switches to `boolean` instead of everything defaulting to `string`.
- **`ScannedCLITool.description`** — tool-level description sourced from the man page `DESCRIPTION`. Subcommand-less tools previously fell back to a bare `Execute <name>`.
- **Empty-scan warning** — a scan that extracts no flags and no subcommands now records a warning instead of silently returning an empty result.
- **`BsdUsageParser`** — fifth built-in parser (priority 95, ahead of GNU) for the single-line bundled usage that BSD/macOS built-ins print when they reject `--help`: `usage: ls [-@ABC...] [--color=when] [-D format] [file ...]`. Expands the bundled group into individual boolean switches, and parses valued short options, long options with inline values, and variadic operands. It claims only text containing a genuine bundled group, so GNU-style help still routes to the GNU parser.
- **git-style subcommand lists** — the GNU parser recognizes prose section intros ("These are common Git commands used in various situations:") in addition to `Commands:` headers, and tolerates command lists split into blank-line-separated labelled groups. `git` previously yielded zero subcommands.
- **`long_running` on an overlay flag** — a machine-readable form of "this option may make the command never terminate on its own". `tail -f` blocked an agent against the harness timeout for a full two minutes during overlay verification, and the only way to say so was prose in a `description`, which no executor can act on. It reaches `ScannedFlag.long_running` and then the emitted contract as the JSON Schema extension keyword `x-apexe-long-running` — an extension rather than a constraint, because `follow: true` is a perfectly valid *value*; what it tells an executor is to bound the timeout or refuse. The claim is **possibility, not certainty**: the BSD man page states `tail -f` returns immediately when its input is a pipe, so a field asserting "always blocks" would be false. Set on exactly four verified flags (BSD `tail -f`/`-F`, GNU `tail -f`/`--follow` and `-F`); flags that merely change how long a follow lasts (GNU `--retry`, `--sleep-interval`, `--pid`, `--max-unchanged-stats`) are deliberately out of scope, since none of them decides termination.
- **`match.platform` is an open string, not an enum** — taken verbatim from `std::env::consts::OS` and normalised to lower case, so `macos`, `linux`, `freebsd`, `openbsd`, `netbsd`, `dragonfly`, `solaris` and anything else a host reports all work without an apexe change. Operating systems are not an enumerable set, and a closed enum would collapse every unnamed one into a lossy `Other` bucket. `ToolVariant` stays an enum for the opposite reason: each member exists only because the classifier can probe for it, and a string would let an overlay declare `variant: "gnu-ish"` and silently never match. There is deliberately no Linux distribution dimension — GNU coreutils `ls` has the same 83 flags on Debian 9.7, Ubuntu 9.4 and Fedora 9.5, while BusyBox `ls` has 21, so divergence tracks the implementation, which `variant` already captures.
- **Single-dash multi-character flags** — an overlay's `short` field accepts `-maxdepth`, `-delete`, `-name`, `-files0-from`. `find`'s entire expression language is built from these, so it was previously inexpressible: validation demanded exactly two characters. A `--long` token misfiled under `short` is still rejected, since validation now checks each field against its own rule rather than walking the merged name list.
- **`docs/overlays.md`** — the overlay authoring guide: when an overlay is warranted, the per-variant verification procedure with exact commands (`man -P cat <tool> | col -b` for BSD, `docker run --rm debian:stable-slim <tool> --help` for GNU, `alpine` for BusyBox), how to fill in provenance, an explicit table of what can and cannot be machine-checked, and the traps already hit in practice.

### Changed
- **Shell completion directories discovered dynamically** — zsh's `$fpath` is queried once per process instead of guessing three hardcoded paths, none of which exist on macOS (system completions live in the version-stamped `/usr/share/zsh/5.9/functions`). Homebrew and distro bash-completion directories are also checked. Tier 3 previously never activated on macOS.
- **Completion subcommand extraction rewritten** — prefers the `_<tool>-<subcommand> ()` function convention that system zsh completions follow; the `commands=(...)` array fallback is now confined to the array body. The previous whole-file scan for `'name:description'` matched `_arguments` option specs, which would have injected phantom subcommands (`_ls` advertises a `formats` spec despite `ls` having no subcommands, and `_git` yielded 131 internal completion tags rather than git's actual commands).
- **BREAKING: `apexe scan --format json|yaml` emits a single `ScanReport` document** — `{ "tools": [...], "commands": [...] }`. Previously each tool was printed as its own document, so a multi-tool scan's stdout was not valid JSON. `commands[]` is a new flattened per-command contract (`id`, `command`, `description`, `risk`, `input_schema`, `output_schema`) for consumers that bind against commands rather than walking the parse tree. Consumers reading the old top-level `ScannedCLITool` shape must now read `tools[0]`.
- **BREAKING: the dormant `user_override` path is gone** — `ParserPipeline::parse` no longer takes `user_override: Option<&Path>`. That hook loaded a `ParsedHelp` YAML document at a layer that cannot see the tool's variant, so it could not express "BSD `ls`, but not the Homebrew GNU one", and `ScanOrchestrator` always passed `None` — it was unreachable. Overriding a scan is now the overlay mechanism's job, reachable via `apexe scan --overlay <PATH>`. An explicitly named overlay outranks every other source and skips the variant, platform and probe conditions it declares; only the command name must still agree, so a mistyped path cannot silently reshape an unrelated tool.
- **Scan cache keyed by variant** — cache entries are now `<name>@<variant>_<version>.scan.json`. A machine holding both BSD `/bin/ls` and Homebrew's GNU `ls` (both reporting no usable version) previously shared one entry, so whichever was scanned last supplied the other's flags.
- **Tool identity normalized to the command name** — `scan /bin/ls` and `scan ls` now produce the same `name`, module id (`cli.ls`), cache entry, and risk annotation; the full path is kept in `binary_path` for execution. Previously an absolute path produced `cli./bin/ls`, skipped man/completion lookup entirely, failed to cache, and mis-inferred risk as `write` instead of `readonly`.

### Fixed
- **Man page parsing was inert on macOS** — `man -P cat` emits nroff overstrike (`D\bD`), so every section header read as `DDEESSCCRRIIPPTTIIOONN` and never matched. Overstrike is now stripped, which is what made Tier 2 reachable at all on BSD systems.
- **Logs no longer corrupt machine-readable stdout** — `tracing` writes to stderr instead of stdout. `scan --format json` interleaved log lines into its own output, so any consumer doing `JSON.parse(stdout)` failed unconditionally.
- **Help error text no longer used as a description** — a tool that rejects `--help` (`ls: unrecognized option '--help'`) had its error message parsed as the tool description; the man page `DESCRIPTION` now takes precedence.
- **`ls@gnu` was missing `--zero`** — found by diffing the overlay against a real GNU coreutils 9.7 `--help` in a container. That overlay had been written without a GNU reference installation: it scored 100% precision but omitted a flag added in coreutils 8.25. Everything present was correct, which is what makes this failure mode hard to notice, and is why provenance is now required.

### Notes
- **No `apexe overlay verify` subcommand was added, deliberately.** A tool can compare flag names; it cannot check descriptions, `conflicts_with`, types or enum values — and those are the reason overlays exist at all. A green check covering only the mechanical half would be read as "this overlay is correct". The verification procedure is documented for humans instead. See "What cannot be automated" in `docs/overlays.md`.

## [0.2.0] - 2026-03-29

### Added
- **6 new `apexe serve` flags** — `--tags`, `--prefix`, `--acl`, `--enable-approval`, `--no-logging`, `--skip-validation` for full McpServerBuilder control from CLI.
- **Expanded help fallback** — Scanner tries `--help all` and `-h` when `--help` yields few flags. Fixes curl (0 → 12 flags on macOS).
- **GNU regex relaxation** — Flag regex now matches 1-space indent (`\s{1,}`) for curl-style help format.
- **`apexe --man`** — Generates complete roff man page via `apcore_cli::build_program_man_page()`, including commands, flags, exit codes, and docs URL.
- **Documentation URL** — `set_docs_url()` sets `https://github.com/aiperceivable/apexe` in help/man output.
- **Explorer `allow_execute`** — `serve_with_options()` enables tool execution from Explorer UI.
- **Env var test stability** — Global `ENV_LOCK` Mutex prevents parallel test race conditions on environment variables.

### Changed
- **Dependencies switched to crates.io** — `apcore = "0.14"`, `apcore-cli = "0.4"`, `apcore-mcp = "0.11"`, `apcore-toolkit = "0.4"`. Zero path dependencies.
- **ACL opt-in only** — `--acl <path>` required to enable access control. Without it, all tools are allowed (fixes Explorer `AclDenied` issue).
- **`require_auth` removed** — Was silently ineffective without JWT authenticator. Removed to prevent false security assumptions.
- **Config override validation** — CLI `scan_depth` (1-5) and `timeout` (>0) overrides now range-checked with warning on rejection.

### Fixed
- **Explorer UI empty response** — Fixed by using `serve_with_options()` with `ExplorerOptions { explorer: true, allow_execute: true }` instead of `serve()`.
- **clippy `result_large_err`** — Suppressed on `execute_subprocess` (Rust 1.94 stricter closure checking).
- **Flaky env var tests** — Eliminated race condition with `ENV_LOCK` mutex.

## [0.1.0] - 2026-03-28

First release with full apcore ecosystem integration.

### Added

**Scanning Engine**
- Three-tier deterministic CLI scanner: `--help` parsing (GNU, Click, Cobra, Clap), man page enrichment (DESCRIPTION + OPTIONS sections), shell completion subcommand discovery
- `ParserPipeline` with automatic format detection and priority routing
- `SubcommandDiscovery` with recursive scanning up to depth 5
- `ScanCache` with JSON filesystem caching and version-based invalidation
- `ToolResolver` with binary path resolution and version detection
- Plugin system via `CliParser` trait for custom parser registration
- Tier 3 completion-discovered subcommands merged back into scan results

**Adapter Layer** (ScannedCLITool → ScannedModule)
- `CliToolConverter`: recursive subcommand tree flattening, dot-separated module IDs (`cli.git.commit`)
- JSON Schema generation with full type mapping: String, Integer, Float, Boolean, Path (`format: path`), URL (`format: uri`), Enum (`enum: [...]`)
- Repeatable flags → array schemas, required flags → `required` array, default value coercion
- Behavioral annotation inference from command names (readonly/destructive patterns) and flag boosting (`--force` → requires_approval, `--dry-run` → idempotent)
- `DisplayResolver` integration: auto-generated MCP aliases (`cli.git.commit` → `git_commit`), per-surface display metadata

**Module Executor**
- `CliModule`: implements apcore `Module` trait for CLI subprocess execution
- Async execution via `tokio::task::spawn_blocking` with `tokio::time::timeout`
- Shell injection prevention: 15-character blacklist validated at construction time and runtime
- Context integration: `trace_id`, `identity`, `duration_ms` propagated through execution
- `ai_guidance` on non-zero exit codes with stderr context for AI self-correction

**MCP Server**
- `McpServerBuilder`: fluent API for module loading → Registry → Executor → APCoreMCP
- Transports: stdio (Claude Desktop/Cursor), streamable-http, SSE
- `LoggingMiddleware` enabled by default (structured logging with redaction)
- `ElicitationApprovalHandler` for interactive destructive command approval (opt-in)
- Tags and prefix filtering for tool access control — **correction (Unreleased):** these filtered `tools/list` only, so an excluded module stayed callable by name. They became access control in Unreleased ([#28](https://github.com/aiperceivable/apexe/issues/28)); read this entry as "tool *listing* filters".
- Explorer UI support (HTTP transports)
- `export_openai_tools()`: OpenAI function calling format export
- Config snippet generation for Claude Desktop and Cursor

**Governance**
- `AclManager`: wraps `apcore::ACL`, auto-generates default-deny rules from annotations
- `AuditManager`: wraps `apcore_cli::AuditLogger`, JSONL append-only with SHA-256 input hashing
- `SandboxManager`: wraps `apcore_cli::Sandbox`, subprocess isolation with timeout enforcement

**Output**
- `YamlOutput`: wraps `apcore_toolkit::YAMLWriter` with optional verification
- `load_modules_from_dir()`: reads `.binding.yaml` files as `Vec<ScannedModule>`

**Configuration**
- 4-tier config resolution: CLI flags > env vars > config file > defaults
- 5 environment variables: `APEXE_MODULES_DIR`, `APEXE_CACHE_DIR`, `APEXE_LOG_LEVEL`, `APEXE_TIMEOUT`, `APEXE_SCAN_DEPTH`
- Optional `apcore::Config` integration via `~/.apexe/apcore.yaml`
- Range validation on all numeric config overrides

**Error Handling**
- `From<ApexeError> for ModuleError`: all 9 error variants mapped with `ai_guidance`
- `into_module_error_with_trace()` for trace_id attachment
- Rich error display in CLI with suggestion text

**CLI**
- `apexe scan <TOOLS>...` — scan with --depth, --no-cache, --format, --output-dir
- `apexe serve` — --transport, --host, --port, --explorer, --name, --show-config
- `apexe list` — --format, --modules-dir
- `apexe config` — --show, --init

**Documentation**
- Quick Start guide (`docs/quickstart.md`)
- Full User Manual with 15 chapters (`docs/user-manual.md`)
- Technical Design document (`docs/apcore-integration/tech-design.md`)
- 7 feature specifications (`docs/features/v2-f1..f7`)
- Feature Manifest with module map (`docs/FEATURE_MANIFEST.md`)

**Examples**
- `examples/basic/` — Shell script walkthrough: scan → list → serve
- `examples/programmatic.rs` — Rust library API: scan → convert → export → build server
